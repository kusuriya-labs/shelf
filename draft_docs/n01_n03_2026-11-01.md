# N01〜N03 実装・検証の記録（2026-11-01）

P0 のうち、数値一貫性（N01）、Prefix Cache の重複キー（N02）、Prefix Cache ×
4 並列（N03）を実装・検証した記録。**N01〜N03 は完了**（2026-11-02、4 モデルで
N01 の 4 並列一致と N03 の全項目を確認）。測定はすべて gfx1201（R9700 32GB）1 枚、
`--pipeline-parallel 1`、greedy（temperature 0）、`--no-eos` で行った。

## N01: FP8 / MXFP4 のバッチ decode 数値経路の統一

### 何が問題だったか

decode の並列数が 1 のときは GEMV（decode1）、2 以上はバッチ GEMM を通る。
両者は同じ数学でも **加算順が違う**ため、logits が一致しない。さらに実装を追うと
次の 3 つが行数で経路を変えていた。

1. FP8 / MXFP4 の線形（decode1 とバッチ GEMM）
2. bf16 の線形（`ExactRows` と `ExactRowsDot2`）
3. GDN の再帰（1 行の decode1 と複数行のチャンク版。チャンク版は hi/lo 分割を
   しないため数値が揃わない）

greedy 生成は argmax なので、この差がトークン境界で列を分岐させる。実際、
27B-FP8 と 35B-A3B では 4 並列と直列で列が分かれた（下の表）。

### 実装

`HipStepExecutorOptions::decode1_max_rows`（既定 4）を追加し、行数がこの値以下の
decode は **1 行ずつ 1 並列と同じカーネル**で回す。

| 対象 | 変更 |
| --- | --- |
| MXFP4 W4A8 | 行ごとに活性化 FP8 量子化 + `launch_gemm_mxfp4_w4a8_decode1` |
| FP8 W8A8 | 行ごとに活性化 FP8 量子化 + `launch_gemm_fp8_w8a8(Decode1)` |
| bf16 | 行ごとに `ExactRows`（`exact_rows = 1`） |
| GDN 再帰 | 行ごとの記述子（`row_req_dev_`）で decode1 を 1 回ずつ発射 |
| swiglu 融合 | 行ごとに `launch_swiglu_quantize_fp8` を発射し、行ごとの並びで置く |

活性化 scratch は行あたり `tiled_bytes(1, k_padded)` の並びになる。融合が作った
コードをそのまま使うため `fp8_owner_rowwise_` を追加した（下の「見つけた欠陥」）。

CLI は `shelf-compute --decode1-max-rows N`（`server.py` も同名で透過）と
`shelf-run` の `PipelineOptions::decode1_max_rows`。`0` で全行バッチ経路に戻せる
（性能比較用。数値は一致しない）。

### GEMV / バッチ GEMM の数値差（実測）

`tests/unit/test_hip_gemm_row_parity.cpp`。同じ 1 行を「1 行 decode1」と「4 行
バッチの同じ行」で計算し、差と argmax を比べる。

| 形式 | features | K | worst abs | 相対 | argmax 不一致 |
| --- | ---: | ---: | ---: | ---: | ---: |
| FP8 W8A8 | 1024 | 2048 | 6.87e-05 | 3.07e-07 | 0 |
| FP8 W8A8 | 3584 | 4096 | 1.53e-04 | 4.13e-07 | 0 |
| MXFP4 W4A8 | 1024 | 2048 | 0 | 0 | 0 |
| MXFP4 W4A8 | 3584 | 4096 | 0 | 0 | 0 |

MXFP4 の decode1 と prefill は **ビット一致**した（同じ K ブロック順で累加する
ため）。差が出るのは FP8 のバッチ GEMM と bf16 の `ExactRowsDot2` である。
差そのものは相対 4e-07 と小さいが、生成が縮退した領域では argmax が入れ替わる
（下の 27B-FP8 の例）。

### E2E: 4 並列と直列の一致

`tests/scripts/check_batch_parity.py`。同じプロンプト（chat template 適用後
20 トークン）を 4 並列で同時に流し、直列 1 本の生成列（64 トークン）と完全一致
するかを見る。

| モデル | `decode1_max_rows=4`（既定） | `0`（全行バッチ） |
| --- | --- | --- |
| Qwen3.5-9B-FP8 | 4/4 一致 | 4/4 一致 |
| Qwen3.8-27B-FP8 | 4/4 一致 | 0/4 一致（列が分岐） |
| Qwen3.8-27B-Quark-AWQ-MXFP4 | 4/4 一致 | 0/4 一致 |
| Qwen3.5-35B-A3B-MXFP4 | 4/4 一致 | 0/4 一致 |

9B-FP8 だけはバッチ経路でも偶然一致した（per-channel 重み・group 0 で差が
小さい）。**一致を保証するのは行ごとの経路**である。

### 性能とのトレードオフ（4 並列・64 トークン・Aggregate）

| モデル | 行ごと（既定） | 全行バッチ | 変化 |
| --- | ---: | ---: | ---: |
| 9B-FP8 | 47.9 tok/s（5.34 s） | 78.8 tok/s（3.25 s） | −39% |
| 27B-FP8 | 16.5 tok/s（15.50 s） | 32.7 tok/s（7.84 s） | −50% |
| 27B-MXFP4 | 16.0 tok/s（16.01 s） | 29.8 tok/s（8.60 s） | −46% |
| 35B-A3B-MXFP4 | 23.0 tok/s（11.15 s） | 25.2 tok/s（10.14 s） | −9% |

1 並列の TPOT は変わらない（9B 28.6 ms / 27B 69.2 ms / 35B 51.0 ms）。行ごとの
経路は層ごとに発射が 4 倍になるため、並列時の実効スループットを落とす。
速度優先の測定では `--decode1-max-rows 0` を使い、**数値一致が要る既定は
行ごと**にする。このコストの回収（バッチ GEMM のまま行ごと同等の加算順にする、
GEMV をまとめて発射する等）は N07 / N12 で扱う。

### 見つけた欠陥と修正

1. **swiglu 融合と行ごとの量子化の取り違え**: 融合は bf16 中間を書かない
   （コードとスケールだけ）。行ごとの経路が入力 bf16 を読み直していたため、
   未初期化の arena を量子化していた。融合側も行ごとに発射し、`fp8_owner_rowwise_`
   が立っているときは量子化を飛ばすようにした。
2. **bf16 の行数依存**: `rows >= 2` で `ExactRowsDot2` に切り替わり、1 行と
   加算順が違っていた。`rows <= decode1_max_rows` は 1 行ずつ `ExactRows` にした。
3. **arena のゼロ初期化フラグが未消費**: `arena_zero_pending_` を立てるだけで
   実際の memset が無く、確保直後の scratch に hipMalloc の残骸が入っていた。
   35B-A3B で「4 並列の 1 スロットだけが直列と違う」現象が 1/3 程度の確率で
   再現し、原因はこれだった。修正後は 18 ラウンド連続で一致（差分 0）。
4. **起動要約が stdout に出ていた**: `boot: ...` を JSONL の stdout に書いており、
   エンジン契約（stdout は JSONL のみ）に違反していた。stderr へ移した。

## N02: Prefix Cache の重複キー管理

### 欠陥

同じ key のブロックを再登録すると `by_key_[key]` を上書きしていた。旧ブロックは
`in_map = true` のまま残り、後で LRU 退避すると `unregister` が
`by_key_.erase(key)` で **新しいブロックの有効な対応まで消していた**。
その結果、登録済みなのに lookup が miss する（キャッシュが黙って消える）。

### 修正

- `insert`: 同じ key が登録済みなら正本を新しいブロックへ移し、旧ブロックは
  private（未登録）にする。参照はどちらも残す。
- `unregister`: map のエントリがそのブロック（と世代）を指しているときだけ消す。

`tests/unit/test_runtime_prefix_cache.cpp` に再現テストを追加した。旧実装では
「旧ブロックは private になる」「退避後も正本で hit する」の 2 件が落ち、
修正後は通る（プール 2 個で、重複登録のあと旧ブロックだけが参照 0 になる形）。

LRU が実際に効いたかを測れるよう `PrefixCache::evictions()` を追加し、
`shelf-compute` が終了時に
`[prefix] stats hits=... misses=... evictions=... blocks=...` を stderr に出す。

## N03: Prefix Cache × 4 並列の E2E

`tests/scripts/check_prefix_parallel.py`。1 プロセスで次を続けて検証する。

1. 空キャッシュで 4 並列（同じ prefix を同時登録）→ 直列と一致
2. 温まったキャッシュで 4 並列（同時 Prefix Hit）→ 一致、hit が 4 件以上
3. 別 prefix ×4 を直列で温めてから 4 並列 → 一致、同時 hit
4. プールを溢れさせて LRU 退避 → 一致、`evictions > 0`
5. 4 並列のうち 2 本を cancel → `cancelled` で返る
6. cancel 直後に同じプロンプトを流す（スロット再利用 + GDN 状態復元）→ 一致
7. エンジンの stdout が JSONL のみ（非 JSON 0 行）

実行例（9B-FP8、`--max-context 192 --prefix-cache-blocks 4 --prompt-tokens 128`）:

```
[prefix] stats hits=14 misses=16 evictions=48 blocks=56
すべて一致
```

`--max-context` と `--prefix-cache-blocks` を小さくしてあるため、9 本の
プロンプト（各 128 トークン = 8 ブロック）でプール 56 ブロックを超え、
LRU 退避が実際に起きる。GDN のスナップショットは 64 トークン地点に取り、
hit 時はその地点まで復元して残りを再計算する（`prepare_prefix`）。

## N03 の結果と、見つかった実行間非決定性

9B-FP8 では上の 7 項目がすべて通る（hits=14、evictions=48、非 JSON 0 行）。
27B / 35B では当初すべての項目が落ちたが、切り分けの結果 **2 つの実行間非決定性**が
原因だった。どちらも修正済みで、エンジン単体の prefill は 9B / 27B-FP8 /
27B-MXFP4 / 35B で 3 回連続ビット一致する。

### 原因 1: ページャブルなホスト配列からの `hipMemcpyAsync`

トークン・位置・スロット・GDN 記述子を、ステップ先頭で `hipMemcpyAsync` により
ホストの `std::vector` から送っていた。ページャブルメモリからの非同期コピーは
**完了順が保証されず**、送信元を同じステップで書き換える（rope の位置配列など）と
内容が不定になる。症状は「最初の decode だけ結果が違う」「同期を 1 回入れると直る」。

修正: 制御データの転送を **同期コピー**（`hipMemcpy`）にした。ステップ先頭は
デバイスが idle（前ステップは同期済み）なのでコストは無視できる。あわせて rope の
位置配列を専用バッファに分けた。

### 原因 2: KV ブロック表の更新が「非同期コピー」で、送信元が一時配列だった

`assign_kv_blocks` はブロック表（ページ表）を `hipMemcpyAsync` で書き換えていたが、
呼び手は `ensure_page` 内の**スタックの一時変数 `&blk`** を渡していた。ページャブル
メモリからの非同期コピーは完了順が保証されないため、コピーが走る前にスタック領域が
再利用され得る（不定の block id が表に入る）。

* 素朴に同期コピーへ変えると、今度は**既定ストリームの同期コピーが非ブロッキングの
  `stream_` 上のカーネルと競合**した（実行中の attention が表を読む横で書き換わる）。
  実測では 9B-FP8 の N03 が LRU 退避の wave で落ちた。
* 正しい形は **`hipStreamSynchronize(stream_)` してから同期コピー**。ページ表の更新は
  page 単位・要求境界なので、この同期のコストは無視できる。

### 原因 3: MXFP4 prefill カーネルの `s_as` 更新後のバリア抜け

`linear_mxfp4_prefill.hip` は 128 K グループごとに活性化スケール `s_as` を差し替えるが、
差し替えの直後に `__syncthreads()` が無く、次の反復の compute が古い値・新しい値を
読む競合があった。N=17408（27B の gate/up）の形で再現し、同じ入力を 2 回実行すると
最大 0.8 の差が出た。修正は差し替え直後のバリア 1 個。

### 原因 4: 最初の decode トークンの位置が 1 つ進んでいた（off-by-one）

prefill の最後の logits からサンプルした最初のトークンは、まだモデルに入力していない。
それなのに `BatchScheduler::decode_result` が **position を進めて**いたため、最初の
decode は位置 `N+1` でトークンを処理し、**位置 N の KV が書かれない**まま attention が
そこを読んでいた。

* prefix cache を使わない場合: 位置 N のブロックは declare で 0 クリア済み。どの構成でも
  同じ 0 を読むので、並列数 1〜4 の比較は一致してしまい、発見が遅れた。
* prefix cache を使う場合: 位置 N のページは**再利用されたブロック**で、前の用途の
  KV が残っている。スロットごとに残骸が違うため、4 並列の decode で**スロットごとに
  logits が変わる**（N=2/3 で偶然一致し、N=4 で露見した理由でもある）。

修正: `decode_result(..., from_prefill)` を追加し、prefill 由来の最初のトークンでは
position を進めない（次に流す decode が位置 `prefilled` で処理する）。

修正後、27B-MXFP4 の「同じ prefix を 4 本同時 hit」は 4/4 一致した。生成列は位置が
1 つずれる前後で変わる（正しい位置になった）。N01/N03 の再測定結果は次節。

### N03 の再測定（原因 1〜4 の修正後）

| モデル | 結果 |
| --- | --- |
| 9B-FP8 | すべて一致（hits=14、evictions=48、非 JSON 0 行） |
| 27B-FP8 | すべて一致 |
| 27B-MXFP4 | すべて一致 |
| 35B-A3B-MXFP4 | すべて一致 |

原因 4（位置の off-by-one）までは、同時 hit の 2 並列・3 並列は一致し 4 並列だけ
最後のスロットが分かれていた。スロットごとの conv/recurrent 状態と KV は 4 本とも
ビット一致し、最初に分かれるのは decode の `attention_gqa_step` だった。位置 N の
KV が未書込み（再利用ブロックの残骸）だったのが原因で、修正後は 4/4 一致する。

## 既知の制約

- 行ごとの経路は 4 並列時のスループットを 9〜50% 落とす（上表）。1 並列は不変。
- `decode1_max_rows` は prefill（行数が多い）には影響しない。端数チャンクが
  4 行以下なら行ごとになる（短いプロンプトのみ）。
- MXFP4 の decode1 と prefill は現状ビット一致するが、この性質に依存せず
  既定は行ごとにしている（カーネルを変えたときに黙って崩れないため）。
- 35B-A3B の MoE は行ごとに実行する。CPU/GPU 分担の数値差（N11）は別途。
- Prefix Cache の hit 一致は **実行間の決定性**に依存する。実行間の非決定性は
  4 件とも修正済み（制御データの転送・ブロック表の競合・MXFP4 prefill のバリア・
  最初の decode 位置の off-by-one）。9B / 27B-FP8 / 27B-MXFP4 / 35B-A3B の
  N03 はすべて一致する。
