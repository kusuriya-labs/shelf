# N08 記録（MoE ルーターの D2H 同期削減、2026-11-02）

対象は N08（MoE ルーティングの GPU 化）。計測は gfx1201 の 1 GPU、
`build/hip-rel`（Release）、モデルは Qwen3.5-35B-A3B-MXFP4（E = 128、top_k = 8）。

## 問題

MoE の 1 行（1 トークン）ごとに、ルーターの logits をデバイスで作って
`hipMemcpyAsync` + `hipStreamSynchronize` でホストへ読み、CPU で top-k を決めていた。
同期は **ストリーム全体を止める**ので、連続バッチングの行数ぶん GPU が待つ。
4 並列の decode では 1 レイヤあたり 4 回、prefill（64 行）では 64 回止まる。

## 実装

1. **複数行のルーターカーネル** `moe_router_logit_rows`（`aux_ops.hip`）を追加した。
   `grid = (experts, rows)`、1 ブロック = 1 (エキスパート, 行)。スレッド分担と
   加算順は 1 行版と同一なので、行ごとの値は 1 行版を rows 回呼んだ結果と
   **ビット一致**する（単体テスト `test_hip_moe_router`）。
2. `moe_mlp` の実行で、rows 行ぶんの logits を 1 回のカーネルで作り、
   D2H と `hipStreamSynchronize` も **1 回** にまとめた。行ごとの `run_moe_row`
   には読み込み済みの logits / 入力を渡す。
3. CPU 分担（pinned のままのエキスパート）が無いときは、入力 x の D2H を
   省略する（top-k には logits だけで足りる）。分担の判定は
   `host_weight_index_` の有無で行う。
4. 実測用に `moe_router_syncs()` / `moe_router_copy_bytes()` を追加し、
   `SHELF_MOE_STATS=1` の `[moe]` 行に出す。
5. 比較用に `SHELF_NO_MOE_BATCH=1` で従来の行ごと同期へ戻せる。

## 測定

4 並列・8 トークン生成（`SHELF_MOE_STATS=1`、1 生成あたりの累計）:

| | 行ごと同期 | まとめ読み |
| --- | --- | --- |
| ルーターの同期回数 | 2400 | **1680**（−30%） |
| ルーターの D2H バイト数 | 2400 KiB | 2400 KiB |
| 生成列 | — | 一致 |

同期回数が行数分の 1 にならないのは、prefill（行数 1 の呼び出しが多い）と
decode（行数 4）が混ざるため。decode だけを見れば 1 レイヤ 1 回になる。

35B-A3B の decode（4 並列、prompt 16 token、max_new 32、`--no-interleave`）:

| | aggregate tok/s | TPOT 中央 / p95 |
| --- | --- | --- |
| 行ごと同期 | 19.6 | 132.8 / 133.7 ms |
| まとめ読み | **20.2** | **126.2 / 127.2 ms**（−5%） |

35B の 4 並列（prompt 64 token、max_new 16）では aggregate 8.6 vs 7.8 tok/s、
TTFT 3597 vs 3988 ms。

## top-k を GPU に置かなかった理由

- 必要な top-k は E = 128 個の f32 から k = 8 個を選ぶだけで、CPU の走査は
  1 行あたり 1000 回程度の比較にすぎない。
- 一方、重みの正規化は **全エキスパートの softmax 和** に依存する。GPU の
  `exp` と CPU の `expf` はビット一致を保証できないため、GPU で和を取ると
  生成列が変わり得る（N01 の T0 を壊す）。
- したがって選択（top-k）と重みの計算は CPU に残し、**同期と転送の回数**を
  減らすことに絞った。logits は E = 128 個（512 B）で、削減しても転送量は
  ほとんど変わらない。

## 残っている課題（N09 以降）

35B-A3B の本当のボトルネックは、ルーターではなく **エキスパートの小さな GEMV** で、
1 生成あたり GPU エキスパート呼び出しが 19200 回（4 並列・8 トークン）になる。
prefill では 64 行 × 8 エキスパート × 3 行列積を 1 行ずつ発射するため、
16 token の prefill に 1.5 秒かかる。N09（同一エキスパートの複数行をまとめる
Grouped GEMM）で、行ごとの発射をグループ単位に減らす。

そのとき、行ごとの累積順（top-1 から順に f32 で足す）を保つために、
エキスパートごとの出力をスロットバッファへ書き、最後に選択順で足す設計にする
（現行の per-row 経路と同じビット列にするため）。
