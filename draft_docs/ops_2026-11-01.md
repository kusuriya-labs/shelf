# 運用機能と外部公開（T18）の実装

状態: 実装済み（HTTP 面の認証・制限・タイムアウト・readiness・metrics・停止制御）
対象: `apps/server/`（OpenAI 互換の HTTP 面）
関連: `draft_docs/serve_protocol.md`（エラー envelope）、
`draft_docs/engine_contract.md`（JSONL）、`apps/server/README.md`（使い方）

---

## 1. 何を入れたか

外部公開に必要な最小限を、既存の HTTP 層（`server.py`）の**1 つの
ミドルウェア**にまとめた。エンジン（JSONL）側の契約は変えていない。

| 項目 | 実装 | 既定 |
| --- | --- | --- |
| 認証 | `Authorization: Bearer` / `X-API-Key` を `hmac.compare_digest` で照合 | 無効（キー空） |
| 同時要求制限 | `inflight >= max_inflight + max_queue` で 429 | 4 + 64 |
| タイムアウト | 1 要求の総時間。非ストリーム 504 / SSE は error + `[DONE]` | 600 秒 |
| readiness | `/readyz` と `/v1/*` の受付可否 | 起動後に有効 |
| エラー統計 | パス×status・code 別・429・timeout・認証失敗 | 常時 |
| 監視 | `/metrics`（Prometheus テキスト） | 常時 |
| 起動・終了 | SIGTERM/SIGINT → 受付停止 → 猶予付き drain → 終了 | 猶予 10 秒 |

## 2. 設計上の判断

### 2.1 認証

* キーは CLI `--api-key` か環境変数 `SHELF_API_KEY`。**空なら認証しない**
  （ループバック開発の既定を壊さない）。
* `/healthz` と `/readyz` は除外する（監視系がキー無しで叩けるように）。
  `/metrics` は**保護する**（生成トークン数などの運用情報を含むため）。
* 比較は `hmac.compare_digest`（長さ・内容のタイミング差を出さない）。
* 失敗は 401 `invalid_api_key` + `WWW-Authenticate: Bearer`。envelope は
  `serve_protocol.md` §1 の 4 フィールドのまま。

### 2.2 同時要求制限

* エンジンは `max_inflight` 本までを同時に流し、残りは `EngineClient` の
  semaphore で待つ。HTTP 層は**待ち行列の長さ**を見て、`max_inflight + max_queue`
  を超えたら 429 を返す（エンジンには渡さない）。
* `inflight` はミドルウェアが `/v1/*` の入口で増やし、`finally` で減らす。
  ストリームは応答を書き終えるまで `inflight` に数える。
* 429 の時点で `queue_rejected` を数える。`Retry-After` は付けない
  （エンジンの空きは要求ごとに変わるため、目安を捏造しない）。

### 2.3 タイムアウト

* 総時間（wall）で判定する。`asyncio.timeout_at(deadline)` を生成ループに掛ける。
* 非ストリーム: `oe.ApiError(504, ..., "timeout")`。`chat` の `finally` が
  ジェネレータを閉じ、`EngineClient.generate` の `finally` が `cancel` を送って
  端末イベントまで drain する（T03 の経路をそのまま使う）。
* ストリーム: ヘッダは送信済みなので status は変えられない。SSE の作法として
  `data: {"error": {...}}` を 1 つ流し、`data: [DONE]` で閉じる。
* **idle timeout（トークン間の無進捗）は未実装**。総時間だけでは「長い生成を
  最後まで待つ」用途に向かないため、必要になったら `--idle-timeout` を足す。

### 2.4 readiness とライフサイクル

* `/readyz` の条件は 3 つ: `ready`（listen 開始後）・`not shutting_down`・
  `client.is_alive()`（エンジン子プロセスの生存）。1 つでも欠ければ 503。
* エンジンが落ちると `is_alive()` が false になり、新しい `/v1/*` は 503。
  処理中の要求は既存の `EngineError`（500 `state_error`）で起こされる（T03）。
* SIGTERM/SIGINT で `shutting_down = True` → 新規は 503。`inflight` が 0 になるか
  猶予時間が切れるまで 50 ms 刻みで待ち、その後 HTTP → エンジンの順に閉じる。
  終了時に `inflight / requests / timeouts / errors` を stderr に出す。

### 2.5 メトリクス

`/metrics` は Prometheus のテキスト形式（依存ライブラリなし）。ラベルの
カーディナリティは固定（パスは既知の 4 本、status は HTTP コード）。

| 名前 | 型 | 意味 |
| --- | --- | --- |
| `shelf_up` | gauge | プロセス生存（常に 1） |
| `shelf_ready` | gauge | 受付可否（3 条件） |
| `shelf_engine_alive` | gauge | エンジン子プロセスの生存 |
| `shelf_inflight` | gauge | 処理中の `/v1/*` 要求数 |
| `shelf_requests_total{path,status}` | counter | パス×status の要求数 |
| `shelf_errors_total{code}` | counter | エラー code 別の件数 |
| `shelf_queue_rejected_total` | counter | 429 の件数 |
| `shelf_request_timeouts_total` | counter | 504 / SSE timeout の件数 |
| `shelf_auth_failures_total` | counter | 401 の件数 |
| `shelf_tokens_generated_total` | counter | 生成トークンの合計 |
| `shelf_request_duration_seconds_sum/count` | summary | 要求の総時間（平均を出せる） |
| `shelf_uptime_seconds` | gauge | 起動からの秒数 |

## 3. 検証

`apps/server/tests/test_ops.py`（8 件、フェイクエンジン・実ポート不要）:

* 認証: 401 / 正しいキー / `X-API-Key` / healthz・readyz の除外 / metrics の保護
* readiness: 起動前 503、ready で 200、停止中 503、エンジン死亡で 503
* 同時要求: `max_inflight=1, max_queue=1` で 3 本目が 429、完了後に `inflight=0`
* タイムアウト: 非ストリーム 504 と**エンジンへの cancel 到達**（`FAKE_CANCEL_LOG`）、
  ストリームは `error` + `[DONE]`
* metrics: 200/400 のカウント、code 別、生成トークン数、summary、uptime

全 pytest は 116 件通過（従来 108 + 8）。`ctest -R serve.python` でも同じ。
