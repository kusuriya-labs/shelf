# 数値の等価性（parity）の方針

状態: 契約（決定済みの方針と、決定に必要な実測手順）
適用先: 協調推論計画のフェーズ 2〜4・量子化（D5）・カーネル変更の回帰・Server のテスト
関連: `draft_docs/directory_design.md` §5、`draft_docs/port_strata_cpu_gpu_coop.md` §4/§6

---

## 1. 方針（決定）

* **主目標は出力トークン列の完全一致**（greedy・固定入力・固定シードで比較する）。
  基準は CPU 参照実装（f32 ゴールデン、`src/backend/cpu/reference_executor.cpp`）。
* **ただし完全一致が成立しない可能性を前提に置く** — WMMA の FMA や累積の順序差は
  hardware / カーネル依存で、dtype 由来の丸めが残る。**許容できるか否かは、
  その dtype の誤差を実測してから決める**（本ドキュメント §3）。
* したがって「許容幅を先に決めてテストを書く」のではなく、
  **誤差の基準値を測り → 合格条件を書く**順序にする。

## 2. 判定フロー（順に適用する）

| 段階 | 内容 | 結果 |
| --- | --- | --- |
| **T0 決定性** | 同一バイナリ・同一装置・同一入力で 2 回以上実行し、トークン列が一致するか | 不一致ならバグ（数値論の前に実行系の問題） |
| **T1 完全一致（主目標）** | CPU f32 ゴールデンと対象実行系（GPU bf16 / 量子化 / 装置を移した配置）の出力トークン列が完全一致するか | 一致なら合格 |
| **T2 誤差由来の判定** | T1 が不一致のとき、**不一致位置の top-1 と top-2 の logits 差（margin）**と、§3 の **dtype 誤差の実測値**を比較 | margin ≤ 誤差規模 → 「丸め由来」として**条件付き合格**（不一致率・最大 divergence を記録に残す）。margin > 誤差規模 → バグとして**不合格** |
| **T3 条件の改訂** | 量子化導入などにより T1 が恒常的に通らない状態になったら | 合格条件そのものを改訂する（改訂は §5 の手続き） |

* T2 の「丸め由来」も、**不一致トークン数と位置を必ず記録する**（再発の追跡と、
  カーネル変更による後退の検知のため）。
* トークン列が一致しない場合の参考指標（logits の最大・平均差、不一致率）を併記するが、
  **これ自体を合格条件にはしない**（主目標はトークン一致のまま保つ）。
* **T0 だけでは足りない（2026-10-28 の実例）**: untied モデルで `lm_head` を埋め込みと取り違える
  バグがあったが、**T0（決定性）は通っていた**（出力だけが劣化）。
  出所と経緯は `draft_docs/shelf_validate.md`「発見したバグと修正」。
  → **初期導入の手順に「外部参照（HF / `transformers`）との同一入力でのトークン列比較」を含める**。
  T0 は「同じ入力を繰り返せば同じ出力」の保証であって、**正しい出力の保証ではない**

## 3. dtype 誤差の実測（フェーズ 0 で一度きりではなく、変更のたびに取り直す）

1. **比較ペア**: 同一入力・同一重みで CPU f32 ゴールデンと対象（初期は GPU bf16。次いで
   bf16 vs **EXL3 4bit**）の **各ステップの logits** を採取
2. **測る値**: max / mean の絶対差・相対差、および**不一致トークン位置での
   top-1 − top-2 margin の分布**
3. **記録先**: 本ドキュメント §6（後述の表）に、装置・dtype・カーネル構成つきで書き込む
4. **許容基準の根拠**として使う値は「margin 分布の p99」を既定とし、
   装置・dtype・カーネルが変わったら**その値を取り直す**
5. 量子化の比較は **`shelf-validate` V1（exact = bf16 9B vs approx = EXL3 4bit 9B）**を最初の対象とし、
   比較ペアを「bf16 実装 vs 量子化実装」に差し替えて同じ手順で基準値を測り直す。
   **4bit は T1 が通らないことが予想されるため、最初の本戦場は T2（margin 判定）になる**
   （EXL3 の誤差特性は codebook / trellis / `head_bits` に依存するので、bf16 比の実測値を
   `shelf-validate` の結果と合わせて §6 に記録する）

## 4. WMMA 固有の注意

* **累積順序はカーネルとレジスタ割当に依存する** — つまり数値が変わる要因は
  「装置の違い」だけではない。**カーネルを差し替えたときも T0 → T1 を通すこと**。
* そこで、**既知入力のトークン列を固定 fixture として保持**し、
  カーネル変更（GEMM・合流点・配置変更）の回帰検査に使う。
  「数値は動くがトークン列は同じ」を守るのがこの fixture の役割。
* 同一バイナリ内での T0（決定性）が T1 の前提。T0 が崩れているのに T2 を議論しない。

## 5. 合格条件を改訂するときの手続き

1. §3 の手順で新しいペアの誤差を測る
2. margin 分布と、実際の不一致トークン位置の関係を確認する
3. 改訂後の条件と測定結果を本ドキュメントに記録し、両計画（§5 / §6）の記述と一致させる
4. 改訂はコード変更と同一コミットに含めない（測定 → 条件更新 → 実装の順に分ける）

## 7. 実装上の含意

* テストは **greedy 固定入力**を基本にする（shelf は greedy 専用: `apps/shelf_run.cpp:4`）。
  sampling（temperature / top_p）は契約次第だが、**基準経路は常に greedy** とする
* テスト出力には「トークン一致・不一致率・最大/平均 logits 差・margin」を必ず含める
* `tests/unit/test_reference_executor.cpp` と `tests/unit/test_hip_*.cpp` の
  parity の作り方を踏襲し、新しい種類の比較はここに集約する
