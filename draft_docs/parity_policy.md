# 数値の等価性（parity）の方針

状態: 契約（決定済みの方針と、決定に必要な実測手順）
適用先: 協調推論計画のフェーズ 2〜4・量子化（D5）・カーネル変更の回帰・Server のテスト
関連: `draft_docs/directory_design.md` §5、`draft_docs/port_strata_cpu_gpu_coop.md` §4/§6

---

## 1. 方針（決定）

* **主目標は出力トークン列の完全一致**（greedy・固定入力・固定シードで比較する）。
  基準は CPU 参照実装（f32 ゴールデン、`src/backend/cpu/reference_executor.cpp`）。
* **ただし完全一致が成立しない可能性を前提に置く** — WMMA の FMA や累積の順序差は
  hardware / カーネル依存で、dtype 由来の丸めが残る。**許容できるか否かは、
  その dtype の誤差を実測してから決める**（本ドキュメント §3）。
* したがって「許容幅を先に決めてテストを書く」のではなく、
  **誤差の基準値を測り → 合格条件を書く**順序にする。

## 2. 判定フロー（順に適用する）

| 段階 | 内容 | 結果 |
| --- | --- | --- |
| **T0 決定性** | 同一バイナリ・同一装置・同一入力で 2 回以上実行し、トークン列が一致するか | 不一致ならバグ（数値論の前に実行系の問題） |
| **T1 完全一致（主目標）** | CPU f32 ゴールデンと対象実行系（GPU bf16 / 量子化 / 装置を移した配置）の出力トークン列が完全一致するか | 一致なら合格 |
| **T2 誤差由来の判定** | T1 が不一致のとき、**不一致位置の top-1 と top-2 の logits 差（margin）**と、§3 の **dtype 誤差の実測値**を比較 | margin ≤ 誤差規模 → 「丸め由来」として**条件付き合格**（不一致率・最大 divergence を記録に残す）。margin > 誤差規模 → バグとして**不合格** |
| **T3 条件の改訂** | 量子化導入などにより T1 が恒常的に通らない状態になったら | 合格条件そのものを改訂する（改訂は §5 の手続き） |

* T2 の「丸め由来」も、**不一致トークン数と位置を必ず記録する**（再発の追跡と、
  カーネル変更による後退の検知のため）。
* トークン列が一致しない場合の参考指標（logits の最大・平均差、不一致率）を併記するが、
  **これ自体を合格条件にはしない**（主目標はトークン一致のまま保つ）。
* **T0 だけでは足りない（2026-10-28 の実例）**: untied モデルで `lm_head` を埋め込みと取り違える
  バグがあったが、**T0（決定性）は通っていた**（出力だけが劣化）。
  出所と経緯は `draft_docs/shelf_validate.md`「発見したバグと修正」。
  → **初期導入の手順に「外部参照（HF / `transformers`）との同一入力でのトークン列比較」を含める**。
  T0 は「同じ入力を繰り返せば同じ出力」の保証であって、**正しい出力の保証ではない**

## 3. dtype 誤差の実測（フェーズ 0 で一度きりではなく、変更のたびに取り直す）

1. **比較ペア**: 同一入力・同一重みで CPU f32 ゴールデンと対象（初期は GPU bf16。次いで
   bf16 vs **FP8 W8A8**）の **各ステップの logits** を採取
2. **測る値**: max / mean の絶対差・相対差、および**不一致トークン位置での
   top-1 − top-2 margin の分布**
3. **記録先**: 本ドキュメント §6（後述の表）に、装置・dtype・カーネル構成つきで書き込む
4. **許容基準の根拠**として使う値は「margin 分布の p99」を既定とし、
   装置・dtype・カーネルが変わったら**その値を取り直す**
5. 量子化の比較は **`shelf-validate` V1（exact = bf16 9B の正本 vs approx = FP8 W8A8 9B の製品版）**
   を最初の対象とし、比較ペアを「bf16 実装 vs 量子化実装」に差し替えて同じ手順で基準値を測り直す。
   **量子化は T1 が恒常的に通らない可能性があるため、本戦場は T2（margin 判定）になる**
   （FP8 W8A8 の誤差特性は **重みの per-channel 静的スケール**と**活性化の per-token 動的スケール**、
   および量子化される Linear の範囲（`linear_attn.*`・`lm_head`・`embed_tokens` は bf16 のまま）に依存するので、
   bf16 比の実測値を `shelf-validate` の結果と合わせて §6 に記録する）

## 3.1 分担（実行する装置）を変えたときの追加規則

CPU/GPU 協調（T17）では、同じ重み・同じ量子化でも**どのエキスパートをどちらで
計算したか**で累積順が変わる。実測（2026-11-01）では 1 エキスパートあたり最大
8e-4 の差が、40 層で増幅して近接 top-1 を入れ替えた。

* 分担を変えた比較は **T1（完全一致）を主目標にしない**。T2 の対象として、
  §6 に「CPU/GPU の分担比・CPU エキスパート数・margin」を記録する。
* **同一の分担**（同じ VRAM 予算・同じ配置計画）なら T0 を要求する。
* 分担をまたいでトークン列を一致させたい要件が出た場合は、量子化境界の扱い
  （例: mid を量子化しない経路）を設計してから T1 を目標に戻す。

### 3.2 量子化の既定（2026-11-01 の変更）

MXFP4 の活性化は **W4A8（E4M3、K 128 要素ごと）を既定**とし、W4A4（E2M1 + E8M0）は
削除した。§6 の表にある W4A4 の行は当時の記録であり、以後の比較は
W4A8 と FP8 / bf16 の間で取る。W4A8 と 27B-FP8 は 8/8 一致（2026-11-01 再測）。

### 3.3 並列数も「実行条件」である（N01）

連続バッチングの並列数（1〜4）を変えると、線形の GEMM が GEMV とバッチ GEMM に
切り替わり、bf16 も `ExactRows` と `ExactRowsDot2` に切り替わる。同じ重み・同じ
入力でも **加算順が変わって logits が動く**ため、並列数は「装置の違い」と同じ
扱いにする。

* 並列数 1〜4 の greedy 生成は **T0（完全一致）** を要求する。
* 既定は `decode1_max_rows = 4`（行ごとに 1 並列と同じカーネル）。
  全行バッチ経路（`0`）は **T2**（argmax と生成品質）の比較用で、T0 の対象外。
* 実測（2026-11-01）: 行ごとで 9B-FP8 / 27B-FP8 / 27B-MXFP4 / 35B-A3B の
  4 並列×64 トークンが直列と一致。全行バッチでは 27B/35B が 0/4 一致。
  性能差（4 並列の Aggregate）は 9B −39%、27B −46〜50%、35B −9%。
  詳細は `draft_docs/n01_n03_2026-11-01.md`。
* 速度優先で全行バッチを選ぶ場合も、**リリース判定は行ごとの一致で取る**。
* N07（2026-11-02）で、2〜4 行を **行ごとに波を割り当てる decode_n** にまとめた。
  行ごとの本文は decode1 と共通で、出力は行ごとの decode1 とビット同一
  （`test_hip_gemm_row_parity` の `decode_n` 節）。したがって 1〜4 並列の T0 は
  そのまま維持される。詳細は `draft_docs/n06_n07_2026-11-02.md`。

### 3.4 実行間の決定性（T0 の前提）

同じ入力・同じ設定で 2 回実行した結果が一致しないと、prefix cache の hit（別の実行が
書いた KV / GDN 状態の再利用）も、並列数違いの比較も意味を持たない。2026-11-01 に
次の 2 件を修正した（詳細は `draft_docs/n01_n03_2026-11-01.md`）。

1. **ページャブルなホスト配列からの `hipMemcpyAsync`**: 制御データ（トークン・位置・
   スロット・GDN 記述子）の転送が完了保証されず、送信元のホスト配列を同じステップで
   書き換えると内容が不定になった。ステップ先頭はデバイス idle なので **同期コピー**に
   変更（`run_impl` の制御データ転送）。
2. **MXFP4 prefill カーネルの `s_as` 更新後のバリア抜け**: 128 K グループの行スケールを
   差し替えた直後に `__syncthreads()` が無く、次の反復の compute が古い/新しい値を
   読む競合があった（N=17408 の形で再現）。
3. **KV ブロック表の更新**: 非同期コピーの送信元がスタックの一時配列で、完了前に
   再利用され得た。同期コピーに変える際も、既定ストリームのコピーが非ブロッキング
   ストリームのカーネルと競合しないよう `hipStreamSynchronize` を先に置く。
4. **最初の decode 位置の off-by-one**: prefill 由来の最初のトークンで position を
   進めており、位置 N の KV が未書込みのまま attention が読んでいた（prefix cache の
   再利用ブロックでは残骸が見え、4 並列でスロットごとに logits が分かれた）。

回帰検査として、カーネル単体で「同じ入力を 2 回実行してビット一致」を見る:
`test_hip_gemm_row_parity`（MXFP4 prefill・活性化量子化）、`test_hip_gdn_chunk`
（チャンク・decode1）、`test_hip_gemm_bf16`（ExactRows rows=1・Prefill2D）、
`test_hip_decode_determinism`（実モデルに近い形で prefill + decode を 2 回）。

## 4. WMMA 固有の注意

* **累積順序はカーネルとレジスタ割当に依存する** — つまり数値が変わる要因は
  「装置の違い」だけではない。**カーネルを差し替えたときも T0 → T1 を通すこと**。
* そこで、**既知入力のトークン列を固定 fixture として保持**し、
  カーネル変更（GEMM・合流点・配置変更）の回帰検査に使う。
  「数値は動くがトークン列は同じ」を守るのがこの fixture の役割。
* 同一バイナリ内での T0（決定性）が T1 の前提。T0 が崩れているのに T2 を議論しない。

## 5. 合格条件を改訂するときの手続き

1. §3 の手順で新しいペアの誤差を測る
2. margin 分布と、実際の不一致トークン位置の関係を確認する
3. 改訂後の条件と測定結果を本ドキュメントに記録し、両計画（§5 / §6）の記述と一致させる
4. 改訂はコード変更と同一コミットに含めない（測定 → 条件更新 → 実装の順に分ける）

**運用上の含意（2026-10-31）**: prefill の行数（チャンク）で結果が変わりうる。サーバ用途では
**プロンプト長から決まる固定のチャンク方針**を使い、同じ入力なら常に同じ列を返すこと
（`shelf-compute` は `--prefill-rows` を固定し、端数は 1 行ずつ積む）。

**2026-10-31 の修正**: 同一プロセスで別シーケンスを流すと結果が変わっていた（T0 が bf16 / FP8 で
`diverged`）。原因は `reset_states` の memset が既定ストリームで走り、実行ストリームと順序が
無かったこと。実行ストリーム上の memset ＋ KV プール／アリーナの初期化で解消（再発防止は
`unit.hip_reset`）。

**未取得**: vocab 全体の logits 差（max / mean）。`shelf-validate` は top-1/top-2 と margin のみ
保持しており、full logits の採取は `shelf-run --out` の `logits_f32.bin` から行う
（同一 ids・同一 step 数で揃えてから §3 の手順で突合する）。

## 7. 実装上の含意

* テストは **greedy 固定入力**を基本にする（shelf は greedy 専用: `apps/shelf_run.cpp:4`）。
  sampling（temperature / top_p）は契約次第だが、**基準経路は常に greedy** とする
* テスト出力には「トークン一致・不一致率・最大/平均 logits 差・margin」を必ず含める
* `tests/unit/test_reference_executor.cpp` と `tests/unit/test_hip_*.cpp` の
  parity の作り方を踏襲し、新しい種類の比較はここに集約する
