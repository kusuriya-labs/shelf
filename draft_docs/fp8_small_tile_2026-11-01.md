# FP8 prefill の小タイル（32/64 行）— 実装と実測

対象: `src/backend/hip/kernels/gemm/linear_fp8_prefill.hip`、
`src/backend/hip/include/shelf/backend/hip/kernels/gemm/detail/linear_fp8_device.h`

## 1. 出発点

FP8 の prefill は 2 本立てだった。

| 経路 | 形 | 前提 |
| --- | --- | --- |
| Prefill2D（64 行 × 64 出力、16 波） | `rows % 64 == 0` | 活性化の読みを 1/4 にする |
| Prefill2D wide（128 行 × 128 出力、8 波） | `rows % 128 == 0` | 活性化を LDS で 8 波が共有 |

32 行・96 行のような**端数タイル**はどちらも組めず、`RowBlock`（1 波・16 出力）へ
落ちていた。MXFP4 では 32 行タイルを足して chunk 32 が約 1.9 倍になったため、
同じ手を FP8 にも入れて測った。

## 2. 実装したこと

- `fp8_prefill2d_wide_body` を `template <kRows, kOutTiles = 2>` にした。
  - `kRows` = 32 / 64 / 128（行タイル）。
  - `kOutTiles` = 1 波が持つ 16 出力タイル数（2 = 32 出力、1 = 16 出力）。
- 端数タイル向けの安全化（128 行経路の生成コードは不変）。
  - 活性化ステージングのストライドを `blockDim.x` に（小タイルは 128 スレッド）。
  - ステージングする行クアッドを「このブロックの範囲」と「総行数」の両方で clamp。
  - 行スケール `s_as` の読みを `min(row, rows-1)` に、格納は `rr >= rows` を捨てる。
  - 使われていなかった `__shared__ s_a[128*128]` を削除（LDS 16 KiB の節約）。
- ランチャは `rows % 64 != 0` かつ `rows >= 32` かつ
  `features % 128 == 0 && k_padded % 128 == 0` のときだけ小タイル wide を選ぶ。
  **64 の倍数の行数は 2 次元タイルのまま**にした。`tests/unit/test_hip_gemm_fp8.cpp`
  の「Prefill2D は RowBlock とビット一致」は `rows % 64 == 0` の形で検査しており、
  ここを wide に変えると累積順が変わって契約が破れるため。

## 3. 実測（Release、256 トークン、3 回の中央値）

9B-FP8（1 GPU）

| chunk | 従来（RowBlock / 2D） | 小タイル wide（32 出力/波） | 小タイル wide（16 出力/波） | 128 行 wide |
| --- | --- | --- | --- | --- |
| 32 | **1,010.5** | 804.2 | 839.4 | — |
| 64 | 1,770.8（2D） | — | — | — |
| 96 | **1,406.0** | 1,406.6 | 1,404.7 | — |
| 128 | — | — | — | 2,478.0 |

27B-FP8（`--pipeline-parallel 2`）

| chunk | 従来 | 小タイル wide |
| --- | --- | --- |
| 32 | **476.9** | 415.0 |
| 96 | **849.3** | 844.1 |

単位は tok/s。小タイル wide は 32 行で 17〜20% 遅く、96 行では同等だった。

## 4. なぜ効かなかったか

- `RowBlock` は **1 ブロック 1 ウェーブ・バリア無し**で回る。32 行・16 出力の
  ブロックが `N/16` 個並び、総ウェーブ数は wide を 16 出力/波に狭めた場合と
  同じになる。つまり並列度で wide の利点が無い。
- wide 本体は活性化を LDS へステージングして `__syncthreads()` で配る。
  行数が 32 だと 1 回のステージング（32 行 × 64 K = 2 KiB）に対して計算が
  小さく、同期と余分なブロック起動がそのまま損になる。
- 32 行では重みの再読みも増える（行あたりの重みトラフィックが 4 倍）。

MXFP4 で小タイルが効いたのは、比較対象が 128 行タイルしか無く（2 次元タイルに
相当する経路が無い）、端数行が極端に遅かったため。FP8 は `RowBlock` という
「小さい行数専用の強い経路」を既に持っているので、同じ手は要らなかった。

## 5. 現在の扱い（実装は取り下げた）

計測が負けたため、**実装は commit 前に取り下げた**。wide 本体（`fp8_prefill2d_wide_body`）
と入口（`gemm_fp8_w8a8_prefill_wide_kernel`）は 128 行専用の元の形に戻してあり、
小タイル用の template・clamp・`SHELF_FP8_SMALL_TILE` は残っていない。
この文書は「試して負けた」記録と数値だけを残すためのもので、再挑戦するときの
出発点になる。

- 128 行経路は元のソースのまま（`unit.hip_gemm_fp8` failures=0）。
- 端数タイル（32/33/96 行）の f64 golden ケースはテストに追加して残した
  （RowBlock 経路の被覆が増える）。

## 6. 残っている観測

1 ステップの壁時計は 9B で

| 行数 | 1 ステップ |
| --- | --- |
| 128 | 51.7 ms |
| 64 | 35.8 ms |
| 32 | 39.8 ms（RowBlock） |

で、行数を 1/4 にしても 8 割までしか縮まない。**1 ステップあたり 20 ms 前後の
固定費**があり、chunk 32 の律速は GEMM ではなくここである可能性が高い。
小タイルの当て推量を続けるより、ステップ固定費（カーネル起動数・グラフ構築・
アリーナ準備）を測るほうが先。この固定費の内訳は未計測。

## 7. 併せて分かった小さな退行（未解決）

同じ比較（Release・HEAD=2eceddb との突き合わせ）で、9B-FP8 の **128 行**だけ
1.5% 遅い（2,690 → 2,653 tok/s。prompt 256/384 の両方で再現、wide を
`SHELF_FP8_WIDE_MIN_K` で切って 2 次元タイルに固定しても同じ、アリーナ固定でも
同じ）。同じ 128 行でも 27B-FP8 は +0.7%、9B-FP8 の 64 行は +5.2%、96 行は +2.1%
なので、系統的な退行ではなく 9B の 128 行に固有の何か（重みの VRAM 配置など）と
見ている。

**原因は 2026-11-01 に特定**: f2fad62 で入った elementwise の x8 版
（`residual_add_bf16_x8` / `bf16_row_slice_vec8`）である。VRAM 配置ではない。
A/B と形状別の測定は `draft_docs/prefill_fixed_cost_2026-11-01.md` §4 を参照。
x8 は 32/64/96 行と 27B の 128 行では勝ち、9B の 128 行だけ負ける（-1.6〜2.2%）。
既定は x8 のまま（64 行で +2〜5%）。
