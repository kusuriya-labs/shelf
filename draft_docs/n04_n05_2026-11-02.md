# N04〜N05 実装・検証の記録（2026-11-02）

P0 の残り、メモリ経路の組み合わせ（N04）と長時間負荷・異常系（N05）の検証。
測定は gfx1201（R9700 32GB）1 枚、`--pipeline-parallel 1`、greedy・`--no-eos`。

## N04: メモリ経路の組み合わせ

### 検証スクリプト

`tests/scripts/check_memory_paths.py`。構成ごとにエンジンを起動し、同じプロンプトで

* A. 直列 1 本（基準）
* B. 4 並列（バッチ decode）
* C. 直列の 2 回目（prefix 有効時は hit）
* D. 4 並列のうち 2 本を cancel し、その後の直列

を流し、生成列の一致・正常終了・HSA fault の有無・stdout が JSONL のみであることを
確認する。起動ログから device / host_weights / host_kv の確保量も記録する。

### 構成と結果

9B-FP8（max_context 512、prompt 96 tok、max_new 8）。

| 構成 | 直列 | 4 並列 | 2 回目 | cancel 後 | 終了 | device / host_weights / host_kv |
| --- | --- | --- | --- | --- | --- | --- |
| baseline | 一致 | 一致 | 一致 | 一致 | rc=0 | 12,315 / 0 / 0 MiB |
| host-kv | 一致 | 一致 | 一致 | 一致 | rc=0 | 12,249 / 0 / 66 MiB |
| host-kv+online2 | 一致 | 一致 | 一致 | 一致 | rc=0 | 12,253 / 0 / 66 MiB |
| host-kv+online4 | 一致 | 一致 | 一致 | 一致 | rc=0 | 12,257 / 0 / 66 MiB |
| prefix | 一致 | 一致 | 一致 | 一致 | rc=0 | 12,323 / 0 / 0 MiB |
| prefix+host-kv | 一致 | 一致 | 一致 | 一致 | rc=0 | 12,249 / 0 / 74 MiB |
| prefix+host-kv+online4 | 一致 | 一致 | 一致 | 一致 | rc=0 | 12,257 / 0 / 74 MiB |
| offload 1024 MiB | 一致 | 一致 | 一致 | 一致 | rc=0 | 10,375 / 1,940 / 0 MiB |
| all（上記の併用） | 一致 | 一致 | 一致 | 一致 | rc=0 | 10,317 / 1,940 / 74 MiB |

27B-MXFP4（max_context 384）でも 9 構成すべて一致（再測定 2 回とも）。device は 17.9 GiB（baseline）→
15.4 GiB（offload 1024 MiB + host KV 116 MiB 併用）。host へ落とした分だけ device が
減り、KV は host 正本 + ミラーになる。

35B-A3B-MXFP4（max_context 384）は baseline / host-kv+online4 / prefix+host-kv+online4 /
offload / all の 5 構成で一致。device 21.3 GiB、host KV 36 MiB、offload 1,024 MiB。

### 注意: MoE の offload は数値が変わり得る

35B-A3B で重みを offload すると、pinned のままのエキスパートは CPU が計算する
（N11 の既知差）。そのため offload 構成は**構成内の一致**（直列 = 4 並列 = 2 回目 =
cancel 後）だけを要求し、baseline との列一致は要求しない。スクリプトはモデルの
`num_experts` を見てこの扱いを切り替える。

## N05: 長時間負荷・異常系

### 検証スクリプト

`tests/scripts/check_stability.py`（モード: `soak` / `crash` / `oom`）。

* `soak`: 4 並列を繰り返し、8 回に 1 回は 2 本を cancel。同じプロンプトは常に同じ
  列になることを検査（prefix hit と cancel の再利用を跨ぐ一貫性）。VRAM を
  `rocm-smi` でサンプルし、増加が閾値以下であることを確認。
* `crash`: 生成中に engine を SIGKILL し、待っている要求がハングせず error で返ること、
  新しいプロセス（再起動相当）で生成できることを確認。
* `oom`: `--vram-budget-mib 1` で起動し、クラッシュではなく予算不足の理由を出して
  非 0 で終了することを確認。

### 結果

| 項目 | 結果 |
| --- | --- |
| soak 200 要求（prefix 32、3 並列なし） | 193 完了 + 7 cancel、error 0、VRAM 増加 0 MiB、rc=0 |
| soak 400 要求（host KV + online4） | 387 完了 + 13 cancel、同一プロンプトの不一致 0、VRAM 増加 0 MiB、rc=0 |
| soak 1200 要求（host KV + online4） | 1162 完了 + 38 cancel、同一プロンプトの不一致 0、VRAM 増加 0 MiB、rc=0（853.8 s） |
| crash（SIGKILL） | 待機中の 4 要求がすべて error で返る（タイムアウトなし）。再起動側で生成成功 |
| oom（予算 1 MiB） | `budget: 必要 12.48 GiB / 使える 996147 B [不足]` を出して rc=1。HSA fault なし |

タイムアウトはサーバ側の `--request-timeout`（pytest `test_ops` の 504 + cancel）で
既に検証済み。エンジンは cancel を受けてスロットを解放する。

### 長時間（1200 要求）

9B-FP8、prompt 32 tok、max_new 4、`--prefix-cache-blocks 32 --kv-in-host
--online-kv-pages 4` で 1200 要求（300 イテレーション × 4 並列、37 回は 2 本 cancel）。

```
soak: 1162 完了 / 38 cancel / 0 error, wall 853.8s, rc=0
VRAM: 初回 12552 MiB / 最大 12552 MiB / 増加 0 MiB
PASS 同じプロンプトは常に同じ列（不一致 0）
```

prefix hit・cancel・スロット再利用を跨いでも同じプロンプトの列が変わらないこと、
VRAM が増えないこと、HSA fault・ハングがないことを確認した。合計 1,800 要求
（200 + 400 + 1,200）を流し、いずれもエラー 0。

## 既知の注意

* VRAM の増加はプロセス全体の使用量（他プロセスを含む）で測る。他に GPU を使う
  プロセスがあると過大に出るため、単独で実行する。
* offline（NSYS 等）を併用するとカーネル実行が変わり、soak の時間が伸びる。
* 27B-MXFP4 の `host-kv+online2` で 1 回だけ cancel 後の不一致を観測した。その後
  同じ構成を 4 回再実行し、6 反復の probe・9 構成の全再測定・1,200 要求 soak
  （online4）では再現しなかった。オンライン KV の窓・リングの扱いを含めて監視項目
  とする（再現したら `SHELF_DEBUG_DECODE_SLOTS` で窓とミラーを突き合わせる）。
