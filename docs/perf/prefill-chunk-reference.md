# prefill chunk の参考測定

2026-11-08、revision `5376403`、R9700 gfx1201 1 枚、TP=1、
`qwen38-27b-exl3-4bpw-mul24`、BF16 KV。`shelf-bench pp --mode forward`、
固定 token ID 1 の合成入力、warmup 1 回・測定 3 回の GPU 時間中央値。
`--arena-gib auto`、page 16。条件ごとに `/tmp/r9700.lock` を取得し、
その間は本測定を単独で実行した。条件の順序は交互ではないため、
既定値の変更を決めるための厳密な比較ではなく参考値である。

| 指定 chunk | 8192 token（ms） | 32768 token（ms） |
|---:|---:|---:|
| 512 | 5781.47 | 27585.43 |
| 1024 | 4947.09 | 24172.23 |
| 2048 | 4753.17 | 23280.52 |
| 4096 | 4393.72 | 21759.56 |
| 8192 | 5472.16 | 26088.72 |
| 16384 | 5451.63（実行は 8192） | 実行不可 |
| 32768 | 5467.65（実行は 8192） | 実行不可 |

32768 token で chunk 16384 以上は `num_tokens exceeds max_num_batched_tokens` で失敗。
8192 token の場合は指定値が prompt 長に切り詰められる。KV 予約量はそれぞれ
514 MiB、2050 MiB。executor の行容量はどちらも 8192 で、chunk 指定ごとの確保量ではない。

このモデルと入力では 4096 は 2048 よりそれぞれ約 7.6%、6.5% 短いが、8192 は遅くなる。
他の形式と MoE を含めた品質・メモリ予算の検証は不足しているため、compute の既定 2048 は
変更しない。mul1 の down_proj（入力幅 17408）では、80 MiB の FP16 xrot が収まる最大行数は
2409 で、それを超えると当該 linear は fused 経路に戻る。mul24 は別の領域分割を使い、
同じ入力幅では dense 経路用領域が 4144 行から 80 MiB を超える計算になる。どちらも
行数だけから求めた境界であり、この測定で境界そのものの dispatch を検証したわけではない。
入力や並行負荷を変えた再測定、他のモデル、複数 GPU は未検証。

追加した `pp` のメモリ表示を用い、同じ条件で各 1 回、warmup なしで確保量を確認した。

| prompt token | executor 作業領域 | KV 予約量 | rank 0 arena 使用量 | arena 物理確保量 |
|---:|---:|---:|---:|---:|
| 8192 | 3977806336 B | 538968064 B | 20407085696 B | 33059504128 B |
| 32768 | 3977806336 B | 2149580800 B | 22017704576 B | 33059504128 B |

arena 使用量は重みを含む。arena の物理確保量は既定の一括確保によるもので、
GPU 全体の実ピークではない。hipBLASLt 等の arena 外確保を含むピークは測っていない。

## chunk 長による出力差（KL）

2026-11-08、同じ revision と GPU。`shelf-bench quality`（teacher-forced）で、`inference-wiki` と
`shelf` の文書を Qwen3.8-27B の tokenizer で連結した 14000 token の corpus を使い、
context を prefill した後の 512〜2048 位置の logits を chunk 長ごとに比べた。
KL は基準（chunk 2048）に対する値で、全語彙の自然対数。context と chunk 長以外は同一で、
同じ chunk 長を 2 回実行すると KL 0・bit 一致だった（実行間の非決定性はない）。

| モデル | context | 比較（基準 → 候補） | 位置数 | KL 平均 | top-1 一致 |
|---|---:|---|---:|---:|---:|
| 27B EXL3-INT8（mul24） | 8192 | 2048 → 4096 | 2048 | 0.264 | 95.2% |
| 同上 | 8192 | 2048 → 1024 | 2048 | 0.278 | 95.2% |
| 同上 | 8192 | 2048 → 8192 | 2048 | 0.310 | 93.6% |
| 27B EXL3（mul1） | 8192 | 2048 → 4096 | 2048 | 0.159 | 96.8% |
| 9B BF16 | 8192 | 2048 → 4096 | 2048 | 0.002 | 98.6% |

27B EXL3-INT8 / mul1 は、context と位置の範囲により KL が大きく変わる（512 位置、基準 chunk 4096 に対する chunk 2048）。

| context | 6144 | 7680 | 8192 | 9216 | 11000 | 4096 以下 |
|---|---:|---:|---:|---:|---:|---:|
| KL 平均（mul1） | 0.0057 | 0.420 | 0.160 | 0.251 | 0.0154 | 0.001〜0.002 |

- 平均 KL は、少数の位置の大きな差に引っ張られている。同じ corpus を Python 版 rocm_exl3
  （同じ mul24 モデル、2048 / 4096）でも測ったところ、context 7680 の 512 位置で KL 平均 0.136・
  中央値 0.00007・p99 2.85・最大 18.5、context 8192 で平均 0.052・中央値 0.00004・最大 20.4 と、
  同じ傾向（大半は 1e-4 以下、数位置だけ数 nat 以上）だった。したがって shelf 固有の
  kernel 不具合というより、この checkpoint と corpus の特定位置で chunk 構成が結果を大きく動かす。
- 原因は特定していない。INT8 活性ではない（mul1 でも発生）。BF16 の 9B では発生しないので、
  EXL3 の fp16 活性経路か、27B の特定 token に対する感度が疑わしいが、未検証。
- 27B の BF16 基準がこの環境で動かせないため、どの chunk 長が真値に近いかは分からない。
  差があること、確定的であること、少数位置に集中していることだけが言える。

したがって chunk 4096 を既定にする判断は、速度（約 6.5〜7.6% 短縮）だけでは足りず、
上の差の原因を調べてから行うべきである。compute の既定 2048 は変更しない。
