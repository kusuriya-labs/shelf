# Qwen3.8-27B 推論エンジン比較レポート（AMD Radeon AI PRO R9700 単体）

**日本語** | [English](engine-compare-qwen38-27b-r9700.en.md)

計測日: 2026-11-23 / 環境: AMD Radeon AI PRO R9700（GPU 1 枚・TP=1・ROCm 10.2・同時実行数 1）

AMD Radeon AI PRO R9700 単体環境で `Qwen3.8-27B` を実行する主要 4 エンジン（`shelf` / `saber-engine` / `hipfire` / `llama.cpp`）について、**生成速度・出力品質・モデルサイズとメモリ効率・ストリーミング安定性・再現性**を同一基準で比較した結果です。

---

## エグゼクティブサマリー

- **速度・品質・モデルサイズのバランス**: `shelf 3.05bpw`（DFlash2 有効）は実務タスク平均 **`104.66 tok/s`**（`chat` は **`87.33 tok/s`** で全構成中 1 位）と高速エンジン群（`saber` `106.56 tok/s`、`hipfire` `103.88 tok/s`）と同水準の生成速度を示しつつ、テキスト推論の実質サイズは **`3.82 bpw`（11.96 GiB）** と `saber W4A8`（`5.27 bpw` / `16.52 GiB`）より約 28% 軽量です。精度重視の `shelf 4bpw` は BF16 基準で **`KL 0.0212` / `top-1 94.76%`** と全構成中最も高い一致度を達成し、実務タスク平均 **`93.98 tok/s`** を記録しました。
- **KV キャッシュ圧縮によるメモリ削減**: 外部考案の KV キャッシュ圧縮方式 `octave:c5v5` に対応しており（今回比較した他 3 エンジンは未対応）、32k コンテキスト分の KV 容量を **`2.00 GiB → 約 0.63 GiB`**（約 68% 削減）に抑えられます。品質への影響は小さく（`4bpw` で `KL 0.0212 → 0.0239`）、DFlash2 併用時の実務タスク平均は `96.65〜98.53 tok/s` です。
- **安定したストリーミング応答**: 停止対策後の連続 200 リクエスト試験（stdio / HTTP × BF16 / `octave:c5v5` 各 50 リクエスト、全 37,783 更新間隔）で **300 ms 以上の停止 0 件（最大 `115.9 ms`）**、さらに今回の 3 構成追加計測（計 114 試行）でも **300 ms 以上の停止 0 件（最大 `117.57 ms`）** を確認しています。
- **量子化から評価までリポジトリ内で再現可能**: 量子化器・形式検証・速度ベンチマーク・BF16 基準の品質評価ツールをリポジトリに同梱しています。配布済み量子化モデルに依存せず、独自にファインチューニングや LoRA マージを行った BF16 モデルも同一手順で量子化・評価できます。

- **`real-v1` / `code` / `chat`**: 英語・日本語のコード編集タスク 6 種（`2k` / `8k` / `16k`）の平均生成速度と、汎用ベンチマークの `code` / `chat` 中央値（`tok/s`）。

- **起動時 VRAM について**: `shelf` と `saber` は既定では空き VRAM の大半（32 GiB GPU で約 `31.5〜31.7 GiB`）を KV / Prefix キャッシュ用に一括予約するため、上表からは省いています。`shelf` では `--arena-gib` オプションにより、生成速度への影響をほとんど伴わずに起動時 VRAM を調節できます（詳細は「トレードオフと留意点」を参照）。

## `shelf` の特徴と実測データ

### 1. 量子化精度とモデルサイズ

- **`shelf 4bpw` は全構成中で最も BF16 に近い品質**: `KL 0.0212` / `top-1 94.76%` を記録しました。2 番手の `llama.cpp UD-Q4_K_S`（`KL 0.0407` / `93.39%`）と比べても KL を約半分に抑えつつ、実タスク平均 `93.98 tok/s` で動作します。
- **`shelf 3.05bpw` は軽量さと品質を両立**: 実質サイズ `3.82 bpw`（`11.96 GiB`）と、`saber W4A8`（`5.27 bpw` / `16.52 GiB`）より約 28% 軽量ながら、`saber` と同等の KL（`0.0597` 対 `0.0595`）および上回る top-1 一致率（`91.11%` 対 `90.62%`）を維持しています。`hipfire MQ4-XTS`（`4.46 bpw` / `KL 0.0851` / `88.53%`）に対しては、モデルサイズ・品質の両面で上回っています。

### 2. 生成速度とストリーミング安定性

- **高速エンジン群と同水準の実用速度**: 同一入力条件での `real-v1` 平均は `shelf 3.05bpw` が **`104.66 tok/s`**（英語 `108.69` / 日本語 `100.64`）となり、`saber`（`106.56 tok/s`）・`hipfire`（`103.88 tok/s`）と同水準、`llama.cpp`（`34.46 tok/s`）の約 3 倍です。
- **汎用タスクでの性能**: `shelf 3.05bpw`（DFlash2）は **`chat 87.33 tok/s`（全構成中 1 位）**、`code 145.37 tok/s`、`json 151.44 tok/s`、`math 160.27 tok/s` を記録しています。
- **量子化ドラフターの品質維持と途切れのない配信**: 量子化版 DFlash2 ドラフター（EXL3-INT8 4bpw）の期待受理長は元 BF16 版と劣化がありません（`4.253` 対 `4.249`）。また、停止対策後の連続 200 リクエスト試験（全 37,783 更新間隔）で **300 ms 以上の停止 0 件（最大 `115.9 ms`）**、今回の追加 3 構成（`4bpw BF16` / `4bpw octave:c5v5` / `3.05bpw octave:c5v5`、計 114 試行）でも **300 ms 以上の停止 0 件（最大 `117.57 ms`）** を確認しています。

### 3. KV キャッシュ圧縮（`octave:c5v5`）

外部考案の KV キャッシュ圧縮方式 **`octave:c5v5`** に対応しており（今回比較した他 3 エンジンは未対応）、32k トークン分の常駐 KV 容量を **`2.00 GiB → 約 0.63 GiB`**（約 68% 削減）に圧縮できます。長文コンテキストや複数セッションを同時保持する用途で有効です（詳細は [kv-octave.md](kv-octave.md) を参照）。

| `shelf` 構成（KV 方式） | 32k KV 容量 | 品質（KL ↓ / top-1 ↑） | 基礎速度 `pp2048` / `tg ctx2048` | DFlash2 `real-v1` 平均 | DFlash2 `code` / `chat` |
| --- | ---: | ---: | ---: | ---: | ---: |
| `4bpw`（BF16） | 2.00 GiB | 0.0212 / 94.76% | 2,324.6 / 31.78 tok/s | 93.98 tok/s | 124.38 / 75.26 tok/s |
| `4bpw`（`octave:c5v5`） | **約 0.63 GiB** | 0.0239 / 94.19% | 2,305.6 / 31.57 tok/s | 96.65 tok/s | 134.24 / 86.27 tok/s |
| `3.05bpw`（BF16） | 2.00 GiB | 0.0597 / 91.11% | 2,350.8 / 35.18 tok/s | 104.66 tok/s | 145.37 / 87.33 tok/s |
| `3.05bpw`（`octave:c5v5`） | **約 0.63 GiB** | 0.0636 / 90.43% | 2,316.9 / 34.93 tok/s | 98.53 tok/s | 145.70 / 76.08 tok/s |

品質変化は小さく（`4bpw + octave:c5v5` でも `KL 0.0239` / `94.19%` と他エンジンより高精度）、非投機の基礎速度への影響も約 1% 前後にとどまります。DFlash2 有効時の `real-v1` 平均は BF16 KV に対して `4bpw` で +2.8%、`3.05bpw` で -5.9% となっており、生成内容や受理率によって変動します。

## トレードオフと留意点

- **Prefill 速度（`pp2048`）の差**: `shelf` の `pp2048` は `2,305.6〜2,350.8 tok/s` であり、`saber`（`4,236.5 tok/s`）・`hipfire`（`5,480.9 tok/s`）の約半分です（`llama.cpp` `1,438.5 tok/s` の約 1.6 倍）。長文プロンプトを毎回新規入力するワークロードでは初回応答時間に差が出ます。
- **KV キャッシュ圧縮の出自**: `octave:c5v5` は外部で考案された KV キャッシュ圧縮方式を `shelf` に実装したものです。
- **既定の起動時 VRAM 一括予約と調整**: `shelf` と `saber` は既定では起動時に空き VRAM の大半（32 GiB GPU で約 `31.5〜31.7 GiB`）を一括予約し、余剰領域をすべて KV / Prefix キャッシュへ割り当てます（一方、`hipfire` は 32k 起動時で約 `16.88 GiB`、`llama.cpp` は約 `19.00 GiB` と必要分のみ確保します）。他プロセスと GPU を共有する場合、`shelf` では `--arena-gib N`（使用上限の目安）または `--arena-gib -N`（他プロセス用に残す空き VRAM の目安）により、生成速度をほとんど変えずに起動時 VRAM を調整できます（減らした分は KV / Prefix キャッシュの余裕容量のみが縮小します）。
- **エンジン間の量子化方式・KV 型の違い**: 各エンジンは異なる量子化形式と既定 KV キャッシュ型を採用しています（`shelf`: EXL3-INT8 + BF16 / `octave:c5v5` KV、`saber`: MACaQ W4A8 + FP8 KV、`hipfire`: MQ4-XTS + FP8 KV、`llama.cpp`: UD-Q4_K_S + FP16 KV）。本レポートは各エンジンの代表的な実用構成どうしの比較です。
- **`saber` の `pp2048` 計測方法**: `saber` では W4A8 パック重みに対する step-capture 計測が利用できなかったため、非投機 API 応答の初回応答時間（TTFT）から算出した近似値を掲載しています（合成 `ctx2048` の decode も出力トークン数が 3 トークンにとどまったため不採用としています）。
- **`shelf 3.05bpw BF16` の計測リビジョン**: 比較表の `shelf 3.05bpw BF16`（DFlash2）速度はストリーミング停止対策前（`9c7be540`）の計測値であり、当時 1 秒以上の停止が発生した 1 試行を除外した正常 38 試行の集計値です。停止対策後（`b9002443`）の連続 200 リクエスト試験および他 3 構成の計 114 試行では、300 ms 以上の停止は 0 件です。
