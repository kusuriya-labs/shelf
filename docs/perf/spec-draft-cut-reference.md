# MTP の draft 長の実測（参考値）

2026-11-08、revision `8fe1478`（旧 `origin/main` `5376403` + 停止位置の修正。**MTP の継続バッチ serve と
verify の chunk 分割（`603f3ca`）が入る前の base での測定**で、現在の main では再測していない）、R9700 gfx1201 1 枚、
TP=1、`qwen38-27b-exl3-4bpw-mul24`（EXL3-INT8）、BF16 KV、`shelf-compute --mtp --temperature 0`、
`--max-seq-len` 1024（1024 token の行は 2048）。CPU とほかの GPU workload が空の状態で、
`/tmp/r9700.lock` を保持して単独実行した。prompt は chat template 適用済みの 3 本
（code: Python の INI パーサ、prose: 英語の説明、ja: 日本語の説明。38〜46 token）。
各条件は生成 256 token を 2 回（n=2）、または 1 回（n=1）測った平均 tok/s（`DECODE_TOKENS_PER_SEC`）。
全条件で `GENERATED_IDS` が非投機の greedy と一致した（同一 prompt・同一生成数）。

生成 1024 token（n=1）:

| 条件 | code | prose | ja | 平均 |
|---|---:|---:|---:|---:|
| 非投機 | 25.9 | 26.5 | 26.3 | 26.3 |
| MTP 固定 4 | 74.0 | 50.1 | 55.2 | **59.7** |
| MTP 固定 7 | 72.1 | 42.7 | 50.6 | 55.1 |
| 固定 7 + `cost` | 68.5 | 44.5 | 53.1 | 55.4 |

要点:

- この環境では固定 4 が最良に近い。code のように受理が高い prompt だけ 6〜7 が数 % 速いが、
  prose / ja では 7 が 4 より 10〜13% 遅い。
- 受理率が高い prompt（code）の平均受理数は固定 7 で 3.6〜3.7、低い prompt（prose）は 1.8 前後。
- `conf` は全 prompt で固定 7 より遅かった。verify 行は減るが、全語彙 logits の host 転送が
  それ以上に効いた。
- `cost` は 256 token では code で固定 7 より速かったが、1024 token では code で遅くなり、
  どの長さでも固定 4 を上回らなかった。探索 round の損失と stream 同期の費用が見える。
- したがって `conf` と `cost`（適応制御）は採用していない。固定長は 4 前後が妥当で、
  `shelf-server` の既定 4 はこの結果と整合する。`shelf-compute` の既定 7 を 4 に下げるかは未決。

制限: prompt は 3 本、生成長は 256 と 1024、条件ごとの反復は 1〜2 回で、分散は評価していない。
DFlash2 は測っていない。MoE と複数 GPU は未検証。
