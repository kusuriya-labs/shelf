# EXL3-INT8 fused GEMM: 17〜64 行（mid-size batch）

バッチ decode（同時 17〜64 request）の EXL3-INT8 GEMM を速くした記録である。対象は
`exl3_mul24_gemm_kernel`（trellis を読むたびに INT8 へ展開して iu8 WMMA に渡す fused kernel）で、
`rows <= 16` は従来の経路、`rows >= 256` は dense（hipBLASLt）経路のまま変えていない。

## 変更前の問題

`rows <= 16` だけが K 方向に split され、17 行以上は split なしだった。grid が `n / 64` block
しかなく（27B の down 形状で 80 block）、デバイスの大半が遊んでいた。33 行以上の MT=4 kernel は
VGPR 236（占有率 6 waves/SIMD）で、decode と WMMA の依存鎖を隠せていなかった。

## 変更

1. **全行数で split-K**: `launch_gemm_bits` が `splits` を 17 行以上にも渡す。分割数は
   `exl3_mul24_gemm_splits` が `n / 16` waves を約 3000 waves に近づけるように決める（上限 16 と
   `groups / 8`、`splits * rows <= scratch_rows`）。1..16 行、17..64 行のそれぞれで分割数は行数に
   依らず一定（batch 内の行数で K の加算順序が変わらない）。65 行以上は分割しない。
2. **row tile 幅を 1/2/3/4 に細分**: 1..16 → MT=1、17..32 → MT=2、33..48 → MT=3、49..64 → MT=4。
   trellis の展開は 1 launch に 1 回のまま、tile 数に応じた VGPR になる。
3. **bits=4 の MT >= 3 は `amdgpu_waves_per_eu(8)`**（VGPR 192 以下）。9 以上は spill で遅くなる。
   MT=4 は 12 B/lane の spill が残るが、占有率 6 → 8 の利益が上回る。**他の bit 幅には適用しない**:
   MT=4・64 行・17408 × 5120 で、4bit は 231 → 185 µs だが、3bit は 180 → 210、5bit は 202 → 276、
   6bit は 207 → 276 µs と悪化する（窓が広く live register が増えて spill する）。bits=6 の lm_head
   （n=248320）も 64 行で 2523 → 3299 µs になるのを統合測定で見つけて切り分けた。27B の重みは 4bit が
   93.5%、6bit が 6.5% である。
4. kernel の block 割り当てを `blockIdx.x = n block * row blocks + row block` に変え、同じ n tile の
   row block が隣接して dispatch されるようにした。17〜64 行（row block は 1 つ）では差が出なかった
   （MT=2 × 2 block で比較）。65 行以上の launch で意味を持つ想定だが、そこは測っていない。

重みを 1 回読む下限は 17408 × 5120 の 4bpw で約 75 µs（約 600 GB/s）である。64 行はまだ 2 倍以上
遅く、MT=4 kernel が主因である。

## 切り分けた仮説

- 活性（A fragment）の再読み出しがボトルネックか: 各 wave が活性全体を読み直すが、読み先を 2 group に
  固定しても 3% しか変わらなかった。coalesced なアドレスにしても 64 行では変わらなかった。
- デコードか WMMA か: どちらか一方を除くと 64 行で 217 → 144〜156 µs になるが、16 行では 7 µs 程度
  しか変わらない。行数が増えるほど、依存鎖と占有率の影響が大きくなる。
- 同じ n tile の row block を 2 回走らせる（MT=2 × 2）: デコードが 2 回になり、MT=4 と同等か遅い
  （200 µs 前後）。MT=3 の 1 回デコードが 48 行で最良だった。

1 step の内訳（semantic timing、ms）:

| 同時数 | step | INT8 GEMM | GDN recurrence |
| ---: | ---: | ---: | ---: |
| 32 | 89.8 → 77.1 | 64.4 → 49.6 | 18.3 → 18.3 |

（75 ms）、次が GDN recurrence（37 ms、1 行あたり約 0.57 ms）である。

## 正しさ

- `test_exl3_mul24_linear` に 17〜64 行の split-K ケース（MT=2/3/4、偶数・奇数・端数の split）を追加した。
  CPU 参照との gemm 相対誤差は 1e-7 台で、既存ケースと同じ。分割数が 17..64 行で一定であることも検査する。
- 旧実装との出力比較（5 形状 × 4 bits × 9 行数、bf16 dump）: 差のある要素は 0.02% 程度で、
  RMS 比 2% 未満（179/180）。残る 1 件は外れ値要素の bf16 1 ulp である。
- 1..16 行の分割数と kernel は変えていないので、decode の出力は変わらない。

## 未対応

- 49〜64 行（MT=4）は 1 周の依存鎖が長い。pipeline の組み直しで更に短縮できる見込みがある。
- GDN recurrence の 1 行あたりの費用（fp16 state の帯域下限の約 2 倍）。
- 活性とスケールの tile 化レイアウト（lookup 数の削減）は、64 行で効果を確認できなかったため見送った。
