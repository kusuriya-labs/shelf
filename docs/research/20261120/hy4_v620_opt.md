# V620 routed expert の単体最適化

2026-11-20 の実験記録。ブランチ `hy4/v620-opt`、worktree は `.worktrees/hy4-v620-opt`。R9700 は別の長時間量子化に使用中のため触らず、V620 1 台（`GPU-08b2ddcbd6e6b36c`、ロック `/tmp/v620.lock`）だけを使った。EP=3 の実機生成は未実施。

## 対象と測定方法

V620（gfx1030）の routed expert 経路は `shelf_hy4_expert_linear`（`src/shelf/kernels/hy4_flash/linear.hip`）で、少数行は `multiply`、8 行以上は `expert_batch16` を使う。どちらも `rotate_input`（FWHT と int8 量子化）→ 内積 → `rotate_output`（逆 FWHT）の 3 カーネルで構成される。

単体ベンチ `tests/kernels/bench_hy4_v620_expert.cpp` を追加した。実装はライブラリの extern "C" 関数をそのまま呼び、合成データ（1536 幅、 Trellis は 4 bpw と同じ 96×96×32 word のレイアウト、入力は有限 BF16、スケールは `rotate_input` が上書き）で代表形状を走らせる。HIP event で warmup 5 回＋計測 80〜100 回の中央値を採用し、最小・最大も併記する。GPU は 1 コマンドごとに `flock /tmp/v620.lock -c ...` で取得し、`timeout` を付け、終了時に解放した。

実重み（4 bpw checkpoint）からの 1 expert 読込は、既存の `test_hy4_flash_layer` が layer 全体の fixture を要求し、単一 expert だけを切り出す経路がないため使わず、形状を合わせた合成データを用いた。正しさは「現行カーネルの出力」および「現行カーネル出力から CPU で計算した swiglu」を基準にしている。

なお空カーネルを同じ event 方式で測ると中央値 17.9 µs で、起動オーバーヘッドが支配的である。これは decode の内積カーネル自体を少しだけ速くしても全体がほぼ変わらない理由であり、カーネル数を減らす融合が最も効果的だった。

各実験で変更→ビルド→正しさ照合→測定→採否→commit を行った。「改善率」は同一ベンチの実行時間中央値から算出した。

## 不採用・途中でやめた案

| 案 | 理由 |
|---|---|
| `unpack_four` を単純なシフト/マスクに置き換える | 4 符号復号は `__umul24(state, 0xdcd12d)` と `udot4` の組み合わせで、単純な `(state >> k) & 0xF` では全 16bit 状態を再現できなかった。GPU と Python のエミュレーションを突き合わせて確認し、等価な単純式がないため見送り |
| グループ 4 行（16 行を 4 バッチ） | 149.72 µs と 1 バッチより 25% 遅い。LDS タイルの再利用が減り、ブロック数増の利点を上回らない |
| 8 行の 2 バッチ分割 | 98.00 µs と 1 バッチ（96.12）より僅かに遅い。閾値は 8 行のままが良い |
| `expert_batch16` のブロックを 256→128 スレッド | 8 行バッチでは半分が遊ぶため一見有利だが、16 行バッチも同じ API で扱う必要があり、行ループの変更を伴う。効果が起動オーバーヘッドに埋もれるため見送り |

## 正しさの確認

- 実験 1・2・3: ベースライン出力バイナリを保存し、新旧の BF16 出力を要素単位で比較。すべて `diff = 0`、`nan = 0`、相対 L2 = 0（bit 一致）。整数の累積順序を変えていないため完全一致が成立する。
- 実験 4・5: ベースライン（gate/up 個別）出力から CPU で clipped swiglu（BF16 丸めを含む）を計算した参照と比較。`diff = 0` で bit 一致。
- `shelf-compute` と `test_hy4_flash_layer` を含む全ターゲットがビルド成功。実機 fixture を使う `test_hy4_flash_layer` の実行は R9700/EP=3 を要するため未実施。

## ボトルネックと考察

- 代表形状の時間はカーネル計算ではなく起動オーバーヘッドが支配的（空カーネル ≈18 µs、1 投影 ≈58 µs のうち大部分）。融合で 6 回だった起動を 3 回に減らしたのが最大の改善要因。
- 内積カーネル自体は `unpack_four` の mul24+udot4 と `sdot4` が密に連鎖しており、ここを削るより起動回数と LDS グループの粒度を変える方が効果が大きい。
- 16 行を 2 バッチに分割すると改善したが、4 バッチにすると悪化する。LDS タイルの再利用と並列度のトレードオフに最適点がある。

## 未実施と今後の確認

- R9700 を含む EP=3 実機（`shelf-compute hy4 generate`、`SHELF_HY4_PROFILE_EP=1`）は今回実行していない。したがって実測の tok/s や rank 別内訳の改善は未検証。
- R9700 が空いたら `with-gpu` 経由で、同じ重み・入力・配置・chunk・seed に対して次を比べる。
  1. pp2048 の prefill 時間。
  2. DFly2 decode（生成 128、先頭を除く 127 token）の tok/s。
  3. `SHELF_HY4_PROFILE_EP=1` の rank 別 HIP event（`expert_ms`）で、V620 rank の gather→3 射影→活性化→加重和の内訳が短縮していること。
  4. CPU 基準との logits 相対 L2 と greedy 列が変わらないこと。
- その際、今回のグループ上限変更は V620 rank のみに適用され、R9700 の WMMA 経路は従来どおり 16 行である点を確認する。

## EP=3 実機検証（2026-11-21）

**判定：不合格。** B は A と logits・greedy 列が一致せず、CPU 基準の誤差も CPU 積和順序対照を超えた。prefill は改善したが DFly decode は低下した。単体の bit 一致から実重みでの同等性を推定できなかった。

A は `96b730b5`、B は `f350c327`。既存 `build-hy4-v620` は ROCm 7.14・gfx1030 のみだったため変更せず、A/B と中間コミットをそれぞれ別ディレクトリに ROCm 10.2、Release、gfx1201 と gfx1030、同一 libc++ でビルドした。GPU は `with-gpu` により R9700、V620、V620 の順に確保。ext4 複製の 4bpw 本体と DFly、従来の Engram と配置を使用し、`ep3-9ao7j7r7` と同一の 2048 token、chunk 1024、温度 0、seed 0、生成 128 token とした。モデル・DFly・配置の report/JSON SHA-256 は従来の settings と一致。A/B/A/B/A/B の別プロセスでそれぞれ 2 回反復し、各初回を除いた 3 回を集計した。decode 分子は先頭を除く 127 token。SHELF_HY4 系環境変数は throughput 測定で未設定。

`fc53aca6` は整数 dot の後にブロックごとの浮動小数点 scale を掛けて加算する処理のワーカー数と加算順序も変更する。「整数の累積順序を変えていないため完全一致」という上記の単体試験の説明は実機全体に適用できない。浮動小数点順序の寄与を層・expert 単位で切り分ける検査は未実施。

さらに `a8dfdf74` 以降の gate/up 融合は gate の `suh` による `rotate_input` を up にも共用するが、実重みの両 `suh` は異なる。例として層 1 expert 0 は 1536 要素中 1516 要素が bit 不一致。単体ベンチは両射影の `suh` と `svh` をすべて 1 にしており、この前提違反を検出できなかった。これは融合経路の明確な不等価要因だが、上記の end-to-end 差への寄与量は未分離。修正と再検証が必要である。

B のソース上、rank 0 の WMMA を使うグループ上限は 16 行のまま、rank 1・2 は 8 行であり、WMMA 分岐の gate/up/swiglu は従来の呼び出しを維持する。ただし 8 行未満の共通 `multiply` は rank 0 でも使われ、`fc53aca6` の変更対象である。WMMA 経路単独の出力一致や各操作の HIP event 内訳は測定していない。

ログ・各版の最終 logits・実行スクリプトは `build-ab/ep3-validation/` に保存した。GPU 確保は A/B と中間コミットの 2 回で、それぞれ `with-gpu` の終了後にサーバーを再起動した。中間コミットは不一致位置の切り分けであり、各コミットの性能中央値は未測定。

## 等価性修正と EP=3 再検証（2026-11-21）

**判定：下記の測定条件では合格。** 最良の検証済み構成 C は 8 ワーカーの元の加算順序、V620 の最大 8 行グループ、修正後の gate/up/swiglu 融合を使う。A は引き続き `96b730b5`。CPU 基準 logits は A と bit 一致、通常生成と DFly の greedy 列は A と一致し、decode 中央値は A 以上だった。prefill は 1.12% 低下したため、すべての速度指標が改善したわけではない。

| 指標 | A | C | C 対 A |
|---|---:|---:|---:|
| pp2048 tok/s（各回） | 686.63、699.78、693.98 | 680.57、686.23、689.05 | — |
| pp2048 tok/s 中央値 | 693.98 | 686.23 | -1.12% |
| DFly decode tok/s（各回） | 52.67、52.54、52.18 | 53.67、53.72、53.71 | — |
| DFly decode tok/s 中央値 | 52.54 | 53.71 | +2.22% |
| 受理候補 / 検証回数（平均受理長） | 94 / 33（2.848） | 94 / 33（2.848） | 一致 |
| CPU 基準 logits 相対 L2 | 0.133337 | 0.133337 | A と bit 一致 |

前回と同じ入力・モデル・配置・seed・chunk で A/C/A/C/A/C を別プロセスで実行し、各プロセス 2 回の初回を除いた。生成 128、decode 分子は 127。4 token 入力の最終 logits は 120832/120832 要素が bit 一致し、今回の A は以前 CPU 比較に用いた A の保存 logits とも bit 一致したため、CPU 相対 L2 を引き継いだ。短入力 24 token および pp2048 後 128 token は、それぞれ通常生成と DFly の両方で A/C 全列一致し、各構成内の通常生成と DFly も一致した。受理長 0〜5 の回数は両方 5、5、5、3、5、10。

### 修正内容と原因の検査

- 融合時の入力回転は 1 起動の `grid.z=0/1` で gate/up を別々に計算し、それぞれの `suh` と独立した int8 codes・scale を使う。出力回転では引き続きそれぞれの `svh` を使う。計算を共有せず、起動回数は増やさない設計とした。mixed checkpoint は読込時に expert 内の 3 射影のビット幅一致を検査する。
- 16 ワーカー変更は `kt` の割当てを `worker + 8n` から `worker + 16n` に変え、各ワーカーの浮動小数点積和と最後の和の順序を変える。LDS 範囲や末尾の明白な誤りはコード上見つからなかった。実重みの 6 行 up の BF16 出力は 1/9216 要素が A と異なり、回転前 FP32 部分和は 6866/9216 要素が異なった（相対 L2 1.28e-7）。少数の丸め差がモデル全体で増幅する可能性と整合するが、この検査だけで加算順序以外のバグを完全に否定したものではない。
- `multiply` と融合 `multiply_pair` を A と同じ 8 ワーカー・同じ逐次加算順序に戻した。A と C の個別射影の回転前 FP32 部分和は、実重みの 1・6 行 gate/up で bit 一致した。16 ワーカーの実重み単体中央値は 1 行約 54.6〜54.7 µs、6 行約 88.4〜88.5 µs、A の 8 ワーカーはそれぞれ約 56.2 µs、89.6 µs（約 1〜3% の速度差、非交互測定）だった。この差より等価性を優先し 16 ワーカー化は外した。
- 単体ベンチは gate/up の異なる `suh`・`svh` を使い、合成値の規模も実 expert の分布に近づけた。`tests/kernels/hy4_v620_fixture.py` でモデルを読み取り専用で切り出した層 1 expert 0 の gate/up/down を使用。実重みと合成データの各 1、6、8、16 行（8 行以上は同一 expert のグループ）で、A の個別 gate/up 射影と GPU 上の元の clipped SwiGLU を組み合わせた参照に対し、C の融合出力は全要素 bit 一致した。単体入力は合成 BF16 であり、実運用時の活性値を保存したものではない。実重み検査は 4bpw の 1 expert に限り、3bpw mixed や他の expert の全数検査は行っていない。

`SHELF_HY4_PROFILE_EP=1` は throughput と別に、A/C 各 2 回実行し初回を除いた。`expert_ms` は gather から加重和までの合計であり操作別の純粋なカーネル時間ではない。

|---|---|---:|---:|

| 1 | V620 | 1323.67 → 1335.32 | 629.92 → 568.04 |

ビルド成功、CPU CTest 2/2 成功。測定・bit 比較のログとスクリプトは `build-ab/ep3-validation/` に保存した。途中、集計スクリプトの標準ライブラリ `bisect` が同じディレクトリの旧 `bisect.py` に遮られ、`with-gpu` を通さず旧検証が誤起動した。確保段階でメモリ不足により失敗し、throughput 3 組の終了後だったが profiling A と重なり旧ログを上書きしたため、旧短入力ログの再生成と profiling A/C の両方を `with-gpu` 内でやり直した。集計スクリプトの import パスも修正した。単体 SwiGLU 検証ツールの libc++ 検索パス不足と 16 ワーカー比較時のライブラリ探索順も修正し、GPU 上で再検証した。
