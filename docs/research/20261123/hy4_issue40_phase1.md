# Hy4-flash のバッチ decode と EP 配置

基準は PR #39 の `5d516cb4`。ROCm 10.2、gfx1201、Release、`SHELF_HY4_ONLY=OFF` で検証した。本体は `Hy4-flash-exl3-4bpw-mul24` と FP8 Engram、drafter は `Hy4-flash-dfly-4bpw` を使用した。GPU 実行は `ROCR_VISIBLE_DEVICES=GPU-a8e9ddefa2d60f55` を設定し、コマンドごとに `/tmp/r9700.lock` を取得した。

## D2　固定射影と grouped MoE

`test_hy4_graph BODY microbench` は層 1〜41 の実 4 bpw 共有 expert の gate（3072 → 1536）を順に処理する。1 周で重み約 97 MB を参照する。固定 FFN は gate、up、SwiGLU、down を通す。routed expert の測定は第 1 MoE 層の全 512 expert を使う。1 行あたり 16 件を選び、41 回の起動で対象をずらし、同じ expert の入力行をまとめる。1 スロットの 6 行 verify は単一スロット用の計画を使う。`moebench` は同じ BF16 入力から実 router を実行し、共有 FFN と加重和まで含める。

実効 GB/s の分子は、対象の固定射影または選択した異なる routed expert の trellis と入出力スケールのバイト数である。分母は 41 回の起動と末尾の同期に要した実時間を 41 で割った値とした。DRAM のハードウェアカウンターは使用していない。固定射影、固定 FFN、expert のウォームアップはそれぞれ 64 周、32 周、5 周とし、続く 5 周の中央値を 1 回の測定値とした。

候補を同一カードで比較した。4 bpw の固定射影で 16 個の K 要素ごとに wave を分けて整数部分和を LDS で足す試作は、1 行 34.53 µs、6 行 40.76 µs で棄却した。K 方向の 128 要素ごとの整数積和をグローバルメモリに書き戻す別の試作は、6 行で約 15.6 µs となったが、同程度の速度を得た LDS 内の実装より広い作業域を必要とした。

**採用**。小さい固定射影は routed expert を多数まとめた場合に比べ実効帯域が低かった。共有 FFN では gate と up を 1 回の grid で処理し、出力回転と SwiGLU を合わせて、down を含む起動回数を 7 回から 4 回に減らした。単独の 6 行射影は 8 分割と加算順を維持し、分割内で使う 3 グループだけを LDS に格納した（19,008 → 2,376 バイト）。行数を実行時の上限から推定した版は約 18.7 µs で棄却し、有効行数を 6 に固定した版を採用した。1 行の単独射影は既存経路を使う。

4 bpw の 1536 × 1536 expert は、1 expert に 1 行だけ割り当てた場合の WMMA を特殊化した。複数行では同じ wave の隣の lane が読んだ trellis の前方ワードを shuffle で受け取り、重なるロードを減らした。expert 内の dot と rank の加算順は維持した。

基準の演算と採用候補を同一ハーネスへそれぞれリンクし、実行順を AB、BA、AB、BA、AB とした。表は各条件 5 回の中央値。各測定で最後の全出力の BF16 ハッシュも照合した。固定射影、FFN、expert、MoE 全体の各条件で、5 回の最大時間と最小時間の比は 1.023 以下だった。

## D3　バッチ Graph

**採用**。稼働中のスロットごとに 1 行の decode または 6 行の verify をまとめて capture し、同じ形状を再利用した。Target の初版は rank 0 の routed expert と共有 FFN を直列に再生した。rank 0 の routed expert を専用 stream に戻した候補では、scatter の完了を全 peer と rank 0 の専用 stream に通知し、共有 FFN を重ねて実行した。層 0 は Engram 入力を集める前に起動した。EP=1 では層 0 と残りの層を 2 回の Graph 起動で実行した。論理 EP=3 の非投機 step は、初版に対し B=4 で約 118.6 → 116.3 ms、B=16 で約 136.5 → 132.5 ms になった。両版とも共有 FFN 融合を有効にした。

同じバイナリと 16 token の入力に対し、Graph を無効・有効の順とその逆順で交互に実行した。1 条件につき 10 step のうち最初の 3 step を除き、残る 7 step の中央値を取り、5 回の中央値を比較した。表は初回 capture と prefill を含まない。非投機の B=1 は単一スロットの `Target::forward`、複数スロットは `Hy4BatchSession::step` の実時間である。

## D4　配置計画

**採用**。Target と DFly2 の実 4 bpw checkpoint のヘッダーを読み、32 GiB のカード、1 台あたり 0.5 GiB の安全余裕、均等な routing 頻度で試算した。rank 0 には shared expert、固定重み、DFly2、KV、index、fold した KV 射影と 2 GiB の作業域を計上した。peer の作業域は 0.5 GiB。新しい配置では全 rank に Graph 用の 256 MiB も計上した。

| 台数 | スロット × 予約長 | routed expert 数（従来 → 今回、rank 順） | 最大数 / 平均数 | 今回の最大使用量（GiB） | 安全余裕控除後の最小空き（GiB） |
|---:|---:|---|---:|---:|---:|
| 3 | 1 × 2,097,152 | 3917 / 8538 / 8537 → 同一 | 1.220 → 1.220 | 29.04 | 2.46 |
| 3 | 16 × 4,096 | 5540 / 7726 / 7726 → 6515 / 7239 / 7238 | 1.104 → 1.035 | 29.58 | 1.92 |
| 3 | 16 × 8,192 | 5487 / 7753 / 7752 → 6515 / 7239 / 7238 | 1.108 → 1.035 | 29.84 | 1.66 |
| 4 | 1 × 2,097,152 | 1783 / 6403 / 6403 / 6403 → 同一 | 1.220 → 1.220 | 21.97 | 9.53 |
| 4 | 16 × 4,096 | 3608 / 5795 / 5795 / 5794 → 4844 / 5383 / 5383 / 5382 | 1.104 → 1.026 | 24.04 | 7.46 |
| 4 | 16 × 8,192 | 3549 / 5815 / 5814 / 5814 → 4844 / 5383 / 5383 / 5382 | 1.108 → 1.026 | 24.31 | 7.19 |

4 台のバッチ配置で rank 0 の routed expert は 23.08%、peer はそれぞれ約 25.64%。この比率は所有数に対する計画値である。実際の負荷はプロンプトの routing と rank 間転送に依存する。物理 3・4 台の step 時間は未測定。

実際の校正頻度（128 × 1,024 token、41 層、計 85,983,232 回の expert 選択）も配置に入力した。16 スロット × 8,192 token のとき、所有 expert の選択回数の最大値 / 平均値は 3 台で 1.0265 → 1.0045、4 台で 1.0342 → 1.0035 だった。rank 0 の所有数に設けた重みを選択頻度にも二重に掛けた候補は、3 台で 1.0345 となったため棄却した。2Mi の既定配置表は 3・4 台とも基準版とバイト一致した。

```bash
python3 tools/hy4_flash/placement.py "$BODY" --draft "$DFLY" --capacity 32 32 32 32 \
    --tokens 8192 --max-concurrent-requests 16
```

## 再現手順と検証条件

採用版の代表的な計測コマンドを示す。BODY は本体と FP8 Engram を含むディレクトリ、DFLY は drafter のディレクトリとする。A/B 比較では同じハーネスを基準の演算にリンクした実行ファイルも使用した。

```bash
export ROCR_VISIBLE_DEVICES=GPU-a8e9ddefa2d60f55
cmake --build build --target test_hy4_graph test_hy4_flash_layer test_hy4_reduce
flock /tmp/r9700.lock build/tests/test_hy4_graph "$BODY" microbench
flock /tmp/r9700.lock build/tests/test_hy4_graph "$BODY" moebench
for batch in 1 2 4 8 16; do
  for draft in - "$DFLY"; do
    flock /tmp/r9700.lock build/tests/test_hy4_graph "$BODY" "$draft" stepbench "$batch" 3
  done
done
```

CPU の層基準は校正列の先頭 4 token を使って `tools/hy4_flash/check_layer.py --layer L --fixture DIR` で生成した。基準版の `test_hy4_flash_layer DIR` による GPU 対 CPU の相対 L2 は、層 0 が 0.01147662、層 1 が 0.00371337、層 2 が 0.00247323。採用版でも 3 層の値はすべて同じで、チャンク 1 と 4 の両方で相対 L2 < 0.04 を満たした。

単一カードの EP 試験は、独立した rank のアリーナ、stream、event を同じ R9700 に割り当てた。通常の `test_hy4_graph` は 42 層を収めるために第 1 MoE 層の routed expert を共有する。これと別に、層ごとに選択される実 expert を常駐させる試験は[PR #39 の照合](../20261122/hy4_pr39_correctness.md)と同じ配置表、16 token の入力、4 token の生成上限を使った。各 rank の配置で B=1 eager の参照列を固定し、各スロットの全 ID と、選択集合外の expert を使用した回数を照合した。物理カード間の PCIe 帯域はこの試験の対象外である。

## 受入結果

- 論理 EP=3・4、push / peer / host、DFly2 有効・無効、Graph 有効・無効を照合した。単一スロット予約の B=1 と、16 スロット予約の B=1・2・4・8・16 を合わせた 144 条件・延べ 768 スロットで、4 token の全生成列が同じ EP の B=1 eager と一致した。EP=3 の参照は `715 17707 67337 11`、EP=4 は `587 269 10044 6896`。選択集合外の参照は 0 件で、各条件の Graph 再生回数も有効化条件と整合した。
- 単一スロットの既存 Graph 試験は EP=1・3・4 で Target と DFly2 がそれぞれ 7/7 一致した。バッチは EP=1 で B=2〜16 の全件数、EP=2〜4 で B=2・4・8・16 を照合した。Target と DFly2 の独立した切り替え、capture 失敗の注入、seed の切り替え、FIFO、キャンセル、スロット再利用、KV 残量が 6 未満の要求との混在、位置 2047・2053 の混在が通った。
- `test_hy4_reduce`、層 0・1・2 の照合、`test_hy4_continuous_batching.py` の全項目が通った。サーバー試験では第 1 層の expert を共有する検証用配置を使用した。
- Release 全体ビルド、CPU CTest 138 件（必須 133 件）、Hy4 の Python 単体テスト 9 件、サーバー CLI 20 件、compute client reader 6 件、grammar protocol 3 件が通った。必須 CPU CTest は最終ビルドでも全件を再実行した。最終の GPU 試験後、排他ロック内で KFD のプロセス数が 0 であることを確認した。
