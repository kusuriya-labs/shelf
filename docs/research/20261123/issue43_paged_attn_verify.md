# DFlash2 の長文 verify で過去の KV ページを共有する

対象は [Issue #43](https://github.com/kusuriya-labs/shelf/issues/43)。基準は `75ff82de`。R9700（gfx1201）1 台、ROCm 10.2、Release、TP=1 で比較した。全実行で `ROCR_VISIBLE_DEVICES=GPU-a8e9ddefa2d60f55` と `flock /tmp/r9700.lock` を使用した。ビルドでは `SHELF_ROCM_ROOT=/opt/rocm/core-10.2`、`CMAKE_HIP_ARCHITECTURES=gfx1201`、`SHELF_LIBCXX_LLVM_ROOT=/tmp/shelf-libcxx23/root/usr/lib/llvm-23` を指定した。

## 結果

16k・8 行・温度 0.7 では通常ラウンドが BF16 で 52.38 → 41.85 ms、FP8 で 55.33 → 42.29 ms、c5v5 で 53.50 → 42.11 ms に短縮した。Issue の BF16 参考値は 52.8 ms、今回の同一入力での短縮率は 20.1% である。採用版の 16 行では c5v5 が 48.26 ms、BF16 が 49.13 ms、FP8 が 49.27 ms だった。

## Octave KV の事前監査

- Graph の判定は target の宣言、verify の行数、要求数、履歴バッファ、tree metadata、サンプリング形状で決まり、3 形式に共通する。変更前の実モデルで 3 形式すべての 8・16 行、greedy・sampled の capture と replay を確認した。
- 24/4・D=256・page 16 は 3 形式とも既存 selector の optimized 範囲に入る。変更前の Octave verify は dispatch から `fused/attention/octave.hip` の split / reduce に進む。`optimized/attention/octave.hip` で KV pool 全体を展開する `launch_octave_kv_dequant` は単体照合の参照値を作るときに使った。1 行の Octave decode は 1 KV head の query head 群で復号結果を共有する。変更前の複数行では各行に別の workgroup を割り当て、ページ走査と bit 展開を繰り返していた。c5v5 は専用 WMMA 経路に入っていた。長文 prefill の 2048-token block に対する逆回転・全展開と、verify の回転空間内の計算は別の経路である。
- 非対称な bit 幅の scalar fallback に正当性の不具合があった。WMMA が 1 回に担当する 16 head の幅で次の group に進む一方、scalar kernel が書く部分結果は最大 6 head 分で、GQA 比 12 では後半 6 head の値が残った。scalar を選んだときは 6 head 刻みに変更した。24 query / 2 KV head の c5v4 で最大絶対誤差が修正前の 1210.21（未初期化領域の値に依存）から 0.0023832 になった。
- Octave の target append は `(row, KV head)` ごとに 1 workgroup で K と V を量子化し、1 回の launch で書く。元の実装では WHT と和の計算を wave 内まで LDS barrier で同期し、最も近い code の選択で最大 64 個の値を線形探索した。wave 内では shuffle を使い、順序付き codebook の隣接する 2 候補を二分探索で特定するようにした。同距離では元と同じ小さい code を選ぶ。
- 単一要求の直列 verify は target の KV に直接 append する。受理後の `append_committed` は target hidden tap を drafter に渡す処理である。drafter の ring は BF16 で、通常の直列 commit は受理位置に合わせて target のページ数を調整する。tree の選択経路を詰め直す処理や prefix cache のページ復元は別経路である。下記の速度比較では prefix cache と tree を無効にした。

Qwen3.8-27B の全 16 attention 層では 1 token の永続 KV は BF16 が 65536 B、FP8 が 33280 B、c5v5 が 20736 B である。16384 token 分はそれぞれ 1.000 / 0.508 / 0.316 GiB。c5v5 は BF16 比で 68.36% 小さい。auto arena は空いた容量も KV ページに使うため、ここでは同じ token 数に必要なバイト数を比較する。

## カーネルの採否

1. 8 行で 3 wave、16 行で 6 wave を使い、各 wave は query 位置と GQA head の組を最大 16 個保持する。同じ workgroup が 1 KV head の 1 split に含まれるページを走査する。各ページの K と転置した V を LDS に置き、全 query で共有する。ページ境界は device 側の位置から算出し、各行に causal mask を適用する。この方式を採用した。
2. FP8 は 8 要素ずつ読み、packed FP8 変換を使う。c5v5 は 5-bit code を 4 個ずつレジスタ内の codebook で変換し、元の decode と同じ近似値で FP16 WMMA を使う。その他の Octave 形式は実際の bit 幅と scale を使う。初期案のスカラー変換では 16k・8 行で FP8 が 404 µs、c5v5 が 278 µs だったため不採用とした（調整用の単体入力）。
3. Octave の Q を各 split で回転する候補は、最適化した c5v5 展開でも 16k・16 行で 250 µs だった。回転を一度だけ実行し、各 split が同じ Q を読む方式を採用した。追加の一時データは既存の attention workspace 内に収まる。V の出力は split の縮約後に一度だけ逆回転する。
4. 複数要求、tree、block mask、対象外の形状、短い可視長には既存の経路を使う。単一要求の長文 verify の選択条件は [カーネルの契約](../../developer/kernels.md) に記載した。

## 実モデルの verify

target は `qwen38-27b-exl3-305-mul24`、drafter は `dflash2-drafter-exl3-4bpw-mul24`。16 行は既存の [Phase 3B と同じ手順](../20261122/dflash2_phase3b.md) で、同じ重みを一時ディレクトリにコピーし `dflash_config.block_size` を 16 に設定した。16 行の受理率はこの重みと入力の組み合わせに固有の値である。

`shelf-compute --serve-stdio` に単一要求を順に送り、`--max-seq-len 16896 --max-concurrent-requests 1 --prefill-chunk 2048 --prefix-cache 0 --dflash2-tree-budget 0` とした。7 または 15 draft、生成上限 128 token、seed 42、top-k 20、top-p 0.95。入力は target の tokenizer で `tools/bench/real_v1/long_16k.txt` を符号化した列を繰り返して必要長まで取り、先頭に ID 248045,846,198、末尾に Phase 2 の `inputs.json` の `short[1].input_ids` を置いた固定長のコード生成課題である。固定形状の verify を比較するために生成上限をそろえた。

A→B、B→A の 2 ペアで実行した。同一プロセス内の要求順は長さの昇順、各長さで greedy、温度 0.7 の順。`SHELF_GRAPH_DEBUG=1` で capture と replay を数えた。`SHELF_DFLASH2_COST_TRACE=1` と `SHELF_DFLASH2_SERVE_STATS=1` を有効にし、行数が所定の `DFCOST` の先頭 2 round を除いた中央値を採った。round はこの区間の wall、verify と draft は GPU event。tok/s は最初と最後の token イベントの受信時刻から求めた要求単位の値で、生成末尾の短縮 round やその要求中の初回 capture を含む。下表は各ビルドの 2 試行の中央値。生成列が異なる場合にも round の固定形状を比較できるが、tok/s には受理数の変化も含まれる。

## 実モデルの KV append

別プロセスの single-shot で `SHELF_GRAPH_VERIFY=0 SHELF_QWEN35_PERF_TIMING=1 SHELF_DFLASH2_VERIFY_TIMING_CSV=...` を設定した。上と同じ入力で最初の所定行数の greedy verify を計測し、16 attention 層の event 時間を合計した。FP8 と c5v5 は独立した `KV_APPEND`、BF16 は K の RMSNorm・RoPE・append をまとめた `attn_kv_preprocess` の所要時間である。BF16 の append 単独時間は融合区間の内訳として測定できない。BF16 には Q 側にも split・RMSNorm・RoPE の融合があり、FP8 と Octave はこの前処理を個別に実行する。表には診断イベントを挿入した eager 実行の単発値を示す。
