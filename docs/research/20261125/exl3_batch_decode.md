# EXL3 のバッチ decode で CPU が重みメタデータの読み取りに費やしていた時間

## 原因と修正

Hy-MT3 1.8B の同時リクエスト数を 1 から 2 に変えると、修正前の
`serve-stdio` では 5.80 ms/step から 29.20 ms/step に増えた。
実験 `EXL3-BATCH-DECODE-1` ではホスト側の `WeightSlot` の参照先を変更し、採用した。

`create_executor` は lowering が作った重みのメタデータを `hipMalloc` の領域に
アップロードしていた。`build_host_execution_context` はホスト側の selector にも
このデバイスポインターを渡していた。projection のグループ化の判定、各 linear の
形状・符号化・stride・plane pointer の取得などが CPU からの VRAM 読み取りになる。
1 リクエストの通常 decode では HIP Graph の replay がこの処理を省く。
複数リクエストの通常 decode は Graph の対象外で、各ステップで同じ処理を繰り返す。
資格条件はキャッシュの検索より前にリクエスト数と token 数がともに 1 であることを
確認する。トレースでも 1.8B は 8 decode 位置のうち `c=1` で Graph launch が 7 回、
`c=2,4,8` はそれぞれ 0 回だった。

executor が lowering 済みの `WeightSlot` の vector を移動して保持し、ホスト側の
dispatch はそれを読む。各 slot が指す重みの実体は従来どおり GPU にある。
GPU の correctness kernel に渡す `DeviceProgramView` はデバイス上の表を使う。
1 ステップごとのコピーや割り当ては追加されない。

## GPU と CPU の時間内訳

R9700（gfx1201）、ROCm 10.2、Release。GPU の実行はすべて
`ROCR_VISIBLE_DEVICES=GPU-a8e9ddefa2d60f55` と `flock /tmp/r9700.lock` で排他した。
`shelf-bench quality` で BF16 KV、128 token を prefill、8 位置を teacher forcing。
入力 token は 0 始まりの位置 i に対して `42 + i % 111`。prefill chunk は 512。
`rocprofv3 --kernel-trace --hip-trace --memory-copy-trace` で末尾 6 ステップを集計した。
以下は各列の中央値（ms）、左が変更前、右が変更後。
区間は GPU の `prepare_batch_descriptor_kernel` 開始から argmax 終了まで。
空き時間は各ステップで区間長からカーネル実行時間の和を引いた値。

両モデルの `c=4` で同じ端点に対応する HIP 呼び出しをホストの時刻で区切ると、
スレッドが HIP API の外で費やした時間は 1.8B が **30.28 → 3.65 ms**、
7B が **29.96 → 3.60 ms**。HIP API 内の合計はそれぞれ 4.20 → 3.94 ms、
4.26 → 3.74 ms。このホスト区間の API 呼び出しは前後とも 3,103 回で、
同期 API の呼び出しは 0 回だった。GPU の処理と CPU の投入は重なるため、
CPU と GPU の表の時間を足し合わせることはできない。トレース自体にも
起動ごとのオーバーヘッドがある。利用者が見る速度は下記のトレースなしの値を使う。

GPU 区間は前後とも 745 起動で、correctness kernel は 0 回だった。
1.8B の `c=4` ではグループ化した projection の rotate・GEMM・出力変換が各 64 回、
単独の GEMM が 65 回（うち語彙 head が 1 回）。128 境界にパディングした head の
`hipMemcpy2D` はホストへの logits 取り出し用で、通常の stdio 生成では呼ばれない。
この GPU 区間の転送トレースも 0 件だった。OPDUMP は演算ごとに stream を同期するため、
通常実行の空き時間の計算には使わなかった。

## serve-stdio の比較

元の Part A と同じ pipe 投入での再現では、Hy-MT3 1.8B の `c=4` が
132.6 → 623.5 tok/s（30.16 → 6.42 ms/step）、7B が 128.1 → 296.6 tok/s
（31.23 → 13.49 ms/step）。共通ブランチの PLaMo-3-Translate-2B EXL3 4.05 bpw
でも 278.2 → 606.6 tok/s（14.38 → 6.59 ms/step）だった。

反復比較では入力到着のずれを除くため、各同時数の JSONL を通常ファイルに書き、
同じ内容を両版の標準入力へ渡した。`shelf-compute --serve-stdio --device 0
--max-seq-len 2048 --prefix-cache 0 --max-concurrent-requests C`、temperature 0、
各リクエストの入力 128 token、生成 128 token、投機なし。Hy-MT3 は Part A の
翻訳プロンプトを用いた。PLaMo は連番の合成 token 列を使い、全条件で 128 token
を生成するよう、同時数 32 の比較は同時数 16 で使った末尾の識別用 token を繰り返した。
各版でプロセスを毎回起動し、実行順を交互に入れ替えた。性能測定は既定の
prefill とトレース無効の本番経路で行った。

集計式は Part A と同じ。`agg_decode_tok_s = C × 127 / max(decode_ms / 1000)`、
1 リクエスト当たりはこれを C で割る。実効 ms/step はその逆数の 1,000 倍で、
最初の token を受け取ったリクエストがほかの prefill を待つ時間も含む。

## 数値と生成列

`quality` は同一 token 列を全リクエストに与え、先頭 sequence の有効語彙全体を
12 位置で dump した。既定経路では PLaMo は全条件でバイト単位の一致。
Hy-MT3 の 1.8B と 7B は全条件で top-1 が 12/12 一致し、
平均 KL の最大はそれぞれ 0.0005151 と 0.0005682 だった。
1.8B の `c=4` は変更前バイナリだけを 3 回再実行しても、最初の変更前 dump に対して
平均 KL が 0.0004170〜0.0005305 になった。既定経路の生成列にも反復間の違いがある。

集約した prefill が 256 行以上になると、Hy-MT3 では行ごとの scale と補正を使う
経路が動く。融合カーネルは補正行の枠を atomic 加算で確保するため、候補が上限を
超えると補正対象が実行順に依存する。入力の JSONL を固定し、
両版で `SHELF_DISABLE_EXL3_ROW_FUSE=1` を指定して、既存の行番号順に補正枠を
割り当てる prefill 経路でも比較した。decode の実行条件はそのままとした。

Hy-MT3 1.8B、7B、PLaMo 2B の `c=1,4,8,16` で、固定 prefill の
全 12 dump が変更前とバイト単位で一致した（平均 KL と最大絶対差が 0）。
同じ条件の `serve-stdio` では全リクエストを独立に greedy 生成し、
87 リクエスト × 128 token、計 11,136 個の生成 ID がすべて一致した。
性能表はこの検証用の環境変数を指定せずに測定した。
