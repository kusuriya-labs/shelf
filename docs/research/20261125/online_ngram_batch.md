# Online N-gram のバッチ検証

## EXP-NG-11　行範囲と出力レイアウト

Hy-MT3 7B BF16 に一般記事、Markdown、ゲーム UI、リリースノートの翻訳を同時投入した。旧実装の `c=4, min_match=4, K=7` では 4 件中 2 件で greedy の出力が変わり、記事の翻訳が 512 トークンで打ち切られた。

- 非ヒットの要求 1 のトレースでは、他の 3 件の verify（各 8 行）の直後に、要求 1 を単独で decode したところで最初の不一致が出た。この時点まで要求 1 自身には verify が一度もなかった。
- 旧 attention プランナーはホストからデバイス上の要求記述子を参照して領域を決めていた。Graph キャプチャ中に記録したコピーは再生時に実行されるため、直前の verify の行範囲で次の 1 行 decode を構築できてしまう。単体テストでは旧記述子を 3 件 × 8 行、現在の記述子を 1 件 × 1 行に固定した。旧ライブラリは失敗し、現在のホスト記述子から組み立てる版は 1 行分のカーネルを選んだ。
- 外部出力にも別の不整合があった。語彙数 128,167 の F32 logits にワークスペース用の行間隔 128,168 が残り、連続テンソルの幅と一致していなかった。トークン ID の I32 出力にも同じ問題があった。外部出力の行間隔とバイト数を修正した版だけでは上記 4 件中 2 件の不一致が残った。
- スケジューラを旧版のまま attention の行範囲を修正すると、同じ 4 件がすべて EOS まで一致した。Graph を無効にした旧版でも、今回の固定投入順での `c=4, min_match=4` は全件一致した。複数要求の合計 verify 行数が 16 を超えると BF16 線形層は通常の小バッチ decode と異なる積和順序を選び得るため、修正版では合計を 16 行以内に抑える。

単一バッチにまとめる際には GDN の巻き戻しも検証した。Qwen3.5-4B BF16 では、decode と verify を混ぜた試作で 4 件中 1 件が不一致だった。再帰履歴の行番号はバッチ先頭が基準だが、畳み込み履歴は要求ごとに 0 行目へ戻っていた。全行分の履歴がある場合は畳み込みもバッチ内の行番号で保存する。修正後は同じ 4 件が EOS まで完全一致し、8 ヒットで 28 個の draft が受理された。GPU テストは、異なるスロットにある 1 行の decode と 4 行・7 行の verify について各行の履歴を個別に照合する。

Qwen3.5-2B BF16 の GDN 形状（畳み込み幅 6,144、value head 16）は履歴保存カーネルの対象外で、旧経路は候補がヒットした時点でエラーになった。単独 N-gram でこの形状を使う場合は、畳み込みと再帰の selector を初期化時に照会して通常 decode を選ぶ。この経路では `c=1,4,8` の全 13 要求が EOS まで一致し、ヒット数は 0 だった。履歴を使う 4B では `c=8` でも 13 ヒット、27 draft 受理、8/8 件一致を確認した。

## EXP-NG-12　同時要求数と検証コスト

Hy-MT3 の要求 1 が 155 番目の出力に達するまでに、baseline は通常の forward を 155 回実行した。旧版は同じ 155 回に加え、8 行を 43 回、16 行を 8 回、24 行を 1 回、計 52 回の独立した verify を実行した。他の要求のヒットで要求 1 の進行が待たされていた。

採用した方式はヒットと非ヒットを同じ forward にまとめ、同時数が大きいときには通常の decode を使う。さらに、3〜7 件で先行する要求の候補を制限した。Hy-MT3 7B BF16 の混在 4 件では、この制限を加える前の 121.4 tok/s から 125.8 tok/s になった。両方とも全要求の出力が一致した。現行の上限と停止条件は [開発者向け仕様](../../developer/online_ngram.md) に記載する。

## EXP-NG-13　測定条件

R9700（gfx1201）、ROCm 10.2、Release ビルドで計測した。変更前は `44fe2b74`、変更後は `b9ca6bf0`。このブランチで直接実行した翻訳モデルは PLaMo 3 Translate 2B / 8B BF16。Hy-MT3 の確認には、同モデルに対応する `41b5f35b` の既存ビルドと、この差分を適用して再リンクした検証用バイナリを使った。

- `shelf-compute --serve-stdio --device 0 --max-seq-len 2048 --prefix-cache 0` を使用した。KV は BF16、temperature は 0、生成上限は 512、最大同時要求数は各ケースの `c` とした。N-gram は `K=7`。集約 tok/s は全要求の生成トークン数（EOS を含む）を、一括投入から最後の done イベントまでの壁時計時間で割った値。
- PLaMo 2B は既存の翻訳評価の Markdown、技術記事、用語集、リリースノートの順に投入した。`c=1` は Markdown のみ、8・16 件では同じ 4 入力を繰り返した。測定用 JSONL を事前にまとめ、プロセスごとに同じ入力で 1 回ウォームアップした。各反復の同じ要求 ID について通常 decode と全生成 ID を照合した。入力の内容は [PLaMo の翻訳評価](../20261124/online_ngram_spec_decode.md) に記録している。
- 実モデルの CTest は短い英日翻訳、識別子の反復、状態名のリストを使う。要求ごとのトークンイベントと done の列、EOS と終了理由、同時実行数、verify 行数、候補のヒットと受理を確認する。以下はモデル配置後の実行例。

```sh
cmake -S . -B build -DSHELF_BUILD_OPTIONAL_TESTS=ON
cmake --build build --target shelf-compute shelf-gpu-test-runner
ROCR_VISIBLE_DEVICES=GPU-a8e9ddefa2d60f55 SHELF_TEST_GPUS=0 \
  SHELF_PLAMO_MODEL_DIR=/home/homelab1/datapool/ai_models/safetensors/plamo-3-translate-2b \
  flock /tmp/r9700.lock ctest --test-dir build -R '^test_online_ngram_batch$' --output-on-failure
```

変更前は元の評価手順で各 1 回再現した。変更後は同じ入力をまとめて投入し、ウォームアップ後の 1 回を示す。速度欄は各ビルドでの通常 decode → N-gram の集約 tok/s。変更前に出力が変わった条件には、打ち切りや生成長の差が含まれる。

### EXL3 の観測範囲

同じ行数制御を適用した Hy-MT3 EXL3 の 8 件同時投入では、ウォームアップ後 2 回の中央値が 7B で 234.63 → 243.46 tok/s、1.8B で 245.96 → 257.27 tok/s だった。全件が EOS に到達した。N-gram と通常 decode のトークン列一致はそれぞれ 13/16、6/16 だった。通常 decode 同士を同じ入力で 2 回比較しても 7B は 6/8、1.8B は 2/8 の一致だった。

7B の別トレースでは、最初の verify は各要求が 300 トークン以上生成した後であり、それ以前にすでに出力の差があった。`min_match=max_match=32768` の対照でもヒットは 0 回で出力差が生じた。これらの速度値は観測値として残し、同一出力での性能比較は BF16 の結果を使う。
