# Qwen4Exp と共通ランタイムへの Hy4-Flash 最適化の移植検証

## 比較条件

基準は `1fb31fd9`。比較には同じホストの R9700（gfx1201、32 GiB）1枚、ROCm 10.2、Release ビルドを使用した。GPU の実行は `ROCR_VISIBLE_DEVICES=GPU-a8e9ddefa2d60f55` と `flock /tmp/r9700.lock` で直列化した。物理 TP はこのホストの測定範囲外である。

モデル計測には `qwen38-27b-exl3-4bpw-mul24` と、3.05 bpw の EXL3 と Ngram4 PLE を持つ `qwen4exp-e2e-link` を使用した。後者はホストに各層448個の expert を配置した。モデル読み込み時間は pp・tg に含めていない。PLE の単体計測はホスト CPU の同じコアで行い、同じ位置を2回ウォームアップしてから11回の中央値を求めた。出力全要素のハッシュも照合した。

入力には PSKLDTOK コーパス（SHA-256 `cd900f38b255d2a62f9e6750c169a1ec10688dffad4d8b782ae7835ad8a67c8f`）の先頭を使った。QSA は `shelf-bench qsa-select --rows 1,16 --blocks 16384,65536 --top-k 512 --compress 4 --warmup 8 --samples 12 --launches 12` で測定する。表のブロック数は圧縮後の個数で、65,536ブロックは262,144トークン相当である。マイクロベンチの時間は同一 GPU の HIP イベントで計測し、比較順を交互にした5組の中央値を使った。

## コードの精査と採否

### EXL3

- BF16 の小バッチ融合に出力行幅と先頭アドレスのアラインメント検査を追加した。入力と出力の範囲が重なる場合は従来のワークスペースを使う。
- 混在投影の元の変更はビット幅ごとに投影全体を繰り返していた。3・4ビットの違いを GEMM の各ワークグループで判定し、入力回転・GEMM・出力回転をそれぞれ1回で処理するようにした。producer 融合には同じビット幅を要求する。
- MT=4 の activation 断片を内側のループでロードする案は、64×5120×5120で 87.457 → 89.765 µs に退行した。従来の事前ロードを採用した。
- WMMA の K 分割について、ゼロ次元、不正な分割数、グリッドの上限を検査した。通常の prefill は分割数1を指定する。複数分割の出力は分割ごとの部分和である。
- GPU テストで HIP の呼び出しに失敗しても成功を返せたため、失敗を終了コードに伝えるようにした。小バッチ融合と混在投影の BF16 出力を全要素で照合する。

### QSA、Hyper-Connections、PLE

- PLE の行列は位置、head、特徴量の順に並ぶ。元の一括処理は n-gram の次数を最外側と解釈して再度転置していた。行番号の列を単一の BF16 変換で処理し、履歴の複製をハッシュに必要な末尾に限った。出力と復号用の作業領域を一括確保し、ホットキャッシュ無効時の排他制御を省いた。
- 旧形式の FP8 PLE で、指数部15の有限値をすべて448として復号していた。共通 E4M3 デコーダーで変換表を生成し、256・288・−448を含む実ファイル形式の回帰テストを追加した。
- RoPE のベクトル化には基底ポインターと前半・後半双方の16バイト整列が必要である。条件外ではスカラー処理を使う。
- QSA の共有カウンターを次の用途に転用する前にブロックを同期する。符号付きゼロの同点をそろえ、選択済みインデックスの昇順整列をブロック全体で行う。top-k は最大1024。最大構成の LDS はヒストグラムと候補を含め49,216バイトである。
- HyperMix の4行版は hidden 2560、4ストリームで、32行が 17.34 → 60.06 µs、256行が 23.13 → 60.57 µs になった。この版を取り除いた。HyperApply はアラインメントを満たす場合にベクトル化する。

### テンソル並列

- argmax のバリアで後着 rank が先着 rank の入力配列を初期化していた。全 rank の入力がそろった時点で検査し、全送信と全受信の登録が完了してから待機スレッドを解放する。
- 語彙分割された行にはグローバルな列オフセットがある。担当区間の先頭から最大値を読み、同点では最小のグローバル ID を採る。全 logits を要求する呼び出し、制約付き生成、確率的サンプリング、出力のないバッチは従来の集約を使う。候補経路は `SHELF_TP_ARGMAX=1` のときだけ有効である。モデルのスケジュールと最大出力行数から、受信・部分和領域およびイベントを事前確保する。
- argmax の送信完了・消費完了イベントを各 rank のデバイスで作成し、その rank のストリームに記録する。他の rank は待機だけを行う。消費完了後にバッファを再利用する。行数拡張前に既存の消費を待つ。
- 片方向フォールバックで、連続する世代・異なる宛先が同じホスト転送領域を使っていた。送信元・宛先・世代の偶奇ごとに領域を確保し、同じ領域の再利用前に受信側の完了を待つ。自己検査で失敗した方向を強制設定で再び有効にする処理を取り除いた。双方向に通信できる2台では既存の StreamSignal を使う。
- TP の終了時は rank のストリームを同期した後、イベント、受信領域、ホスト転送領域を解放する。途中でエラーが起きても残りの解放を試し、最初のエラーを呼び出し側へ返す。
- 4入力の単独 reduce は送信元 rank 順に加算し、各 rank で丸め順をそろえる。整列した入力は16バイトずつ読んで加算する。物理リンクに対する検証には2台または4台の同型機が必要である。

### サービング

- 受理トークン数の絶対値に基づく判定では、大バッチで K=3 からの上昇しきい値が K 自体を超えていた。各ラウンドの受理率を平滑化し、8ラウンド以上の間隔で一段ずつ切り替える。K=2 で毎回1個を受理する場合も上昇できることをテストする。
- prefill を中断するときにリクエスト列だけを間引くと、KV ページの割り当て判定が別のリクエストを参照する。全リクエストを元の順序で渡し、decode を実際に確保できたときにそのステップを終了する。
- キャンセル直後に遅れて届いた `draft_masks` が次の要求にエラーを漏らしていた。対象要求が終了済みなら未処理のマスクは存在しないものとして扱う。
- `ignore_eos` を MTP のバッチ検証・逐次フォールバック・受理後の打ち切り判定まで渡す。単一デバイスで要求ごとに drafter を持つ MTP 経路でも実際の forward 回数を数え、生成中のページ境界で drafter のスナップショットを保存する。agentic ベンチでは途中で切れた SSE を失敗とし、ストリーム更新間隔とトークン単位の出力時間を区別する。TTFT の分位点を算出できない場合は空欄にする。

Qwen4Exp の MTP では、共有ドラフターに加えて全要求分の GDN スナップショットと検証履歴を確保する。単一 GPU の容量計算がこの状態を落としており、ドラフター予約が0.42 GiBのまま起動時に枯渇した。実行時と同じ行数・文脈長で容量を見積もり、融合検証の状態を加えた。また、作業領域を6 GiB指定しても、既に確保済みの executor との差額を確保せず、KV 予算が18.32 GiBのままだった。明示指定の場合は差額を先に残して KV ページ数を決める。修正後は同じ8要求・6 GiB指定でドラフター予約が1.43 GiB、KV 予算が11.98 GiBとなり、起動と正常終了を確認した。

イベントの記録箇所は TP transport 内の6か所を確認した。

| イベント | 作成するデバイス | 記録するストリーム | 利用側 |
| --- | --- | --- | --- |
| `sent_[r][q][p]`（通常コピー、producer 書き込み済みの2か所） | r | r の実行ストリーム | q が待機 |
| `consumed_[r][q][p]` | r | r の実行ストリーム | q が同じ受信領域を再利用する前に待機 |
| `lm_sent_[r]` | r | r の実行ストリーム | 他 rank が受信前に待機 |
| `lm_done_[r]` | r | r の実行ストリーム | 次回の sender が再利用前に待機 |
| `probe_ready_[r]` | r | r の検査用ストリーム | 起動時の通信検査 |

単一 GPU 上の回帰テストでは、2本のストリームとホスト転送を使い、行数を1〜3で繰り返し変えて32回の argmax を実行した。4 rank の加算は `[1e20, −1e20, 1, 2]` を使い、全 rank の結果が3になることを照合した。

### 小バッチの適用形状

ランダムな重みを128 MiB以上の作業領域で交代させ、基準版の split-K 選択を有効にした。各プロセス内でウォームアップ後に20起動の組を5回計測し、さらに基準・候補の順序を反転した5組の中央値を取った。

| 行数 | 入力 → 出力 | 基準の3段処理（µs） | 単一カーネル（µs） | shuffle 併用（µs） | 既定の選択 |
| ---: | --- | ---: | ---: | ---: | --- |
| 1 | 5120 → 17408 | 96.379 | 108.709 | 88.775 | 従来経路。明示指定時は−7.9% |
| 1 | 5120 → 512 | 20.040 | 76.087 | 28.848 | 従来経路 |
| 8 | 5120 → 5120 | 42.650 | 102.103 | 68.847 | 従来経路 |
| 16 | 17408 → 5120 | 108.365 | 986.679 | 644.224 | 従来経路 |

4ビットでは隣接レーンが持つ trellis word を再利用できる。従来の N-major 配置でも同じ関係が成り立つので、重みを再配置せずに shuffle を使った。比較対象16形状のうち、入力5120・出力17408の1行だけが基準より速かった。ただし基準の split=4 と融合の split=1 では加算順が異なり、同じ乱数入力で BF16 出力17,408個のうち6個が異なった（最大絶対差0.125、出力の最大絶対値340）。このため最速の形状を含めて明示指定に限定した。非融合時のエピローグ用 LDS 宣言は1要素になり、例えば MT=4 では宣言上32,768 → 4バイトとなる。コンパイラが除去する未使用領域もあるため、宣言量の差から速度を推定していない。

| モデル・条件 | 基準版 | 統合版 | 単位・条件 |

| Qwen3.8-27B EXL3、pp | 1,781.46 | 1,788.42 | tok/s。512トークン、warmup 1、5回 |

Qwen3.8-27B の固定入力では32個の生成 ID が一致した。`shelf-bench batch` の4要求も各24個すべて一致した。このベンチの同時実行枠は1なので、同時要求の性能には stdio サーバーの結果を使う。Qwen4Exp でも最終の既定設定で16個の生成 ID が一致した。ウォームアップなしの一回の `shelf-compute` では、Qwen4Exp の prefill は2,647 → 3,715 ms、decode は8.85 → 7.81 tok/s であった。

同じサーバーを起動したまま Qwen4Exp の128トークン要求を繰り返すと、2回のウォームアップ後5回の TTFT 中央値は 1,354.27 → 1,353.38 ms、decode は 11.68 → 11.77 tok/s だった。短い入力では全7回の16個の生成 ID が一致した。4,096トークンでは最初の16個が基準と一致し、次の2回は12個目で分岐した。expert キャッシュの入れ替え回数も異なった。この2回の TTFT は 35.082 → 35.090 秒、decode は 15.81 → 15.63 tok/s で、異なる生成列を含むため速度の採否には使わない。長文入力の PSKLDTOK の SHA-256 は `0cc3f34918564bb18bde53378437b46ee91d94866cc9b775c49625a1602d719e`。

同じ動的設定で両版を別プロセスから起動し直し、128トークンの要求7回に続いて4,096トークンの要求を3回送った。短文・長文とも全回で両版の16個の生成 ID が一致した。長文の後半2回の TTFT 中央値は35.201 → 35.170秒だった。初回に観測した分岐はこの再試験では再現しなかった。

分岐直前の11個の ID を同じ4,096トークンに加え、4,107トークンの固定入力でも照合した。両版とも `--moe-cache-swap-budget 0 --moe-host-experts 448 --prefix-cache 0 --prefill-chunk 128 --dump-logits` を使用した。最終 prefill と生成中に記録した4行・計993,280個の FP32 logits はビット単位で一致し、最大絶対差と KL はともに0だった。生成 ID は両版とも `3150,2557,931`。分岐位置の上位2語の差は0.34147だった。この比較では expert 配置と入力を固定しており、動的な入れ替え中に起きた差の原因は特定していない。入れ替え可能量は PCIe 予算の実時間ベースの補充にも依存する。最後の照合に用いた NVMe 上の一時コピーは全ファイルの SHA-256 を元のチェックポイントと照合した。

## 物理マルチ GPU の試算

語彙数を V、rank 数を P とする。従来の語彙出力は各 rank が幅 V の FP32 行を他の全 rank に送る。argmax は各 rank が最大値と ID の8バイトを送る。1行あたりの全リンク合計送信量はそれぞれ `4V × P(P−1)` と `8 × P(P−1)`。受信を重ねて数えていない。V=248,320 ならどちらの台数でもペイロードは 1/124,160 になる。

| 構成 | 従来の送信量 | argmax の送信量 | 片方向実効25 GB/s と仮定した送信元1台あたりの直列転送時間差 |
| --- | ---: | ---: | ---: |
| R9700 ×2 | 1,986,560 B/行 | 16 B/行 | 39.73 µs/行 |
| R9700 ×4 | 11,919,360 B/行 | 96 B/行 | 119.19 µs/行 |

実測した各 rank のローカル処理時間を以下に示す。基準は全幅 FP32 の加算と、本番 selector が選ぶ64分割のサンプリング。候補は担当語彙の pack と受信済みペアの reduce。すべて単一 GPU 内で実行し、P2P 転送・CPU バリア・イベント待機を計測から外した。移植当初の1ブロックの語彙走査は小バッチで律速になったため、長い語彙は64ブロックに分けて行内最大値を集約する。

| 想定 rank 数 | 行数 | 基準の加算＋サンプリング（µs） | 移植当初の pack＋reduce（µs） | 採用版の pack＋reduce（µs） |
| ---: | ---: | ---: | ---: | ---: |
| 2 | 1 | 15.92 | 100.58 | 12.35 |
| 2 | 32 | 119.05 | 99.41 | 48.69 |
| 4 | 1 | 15.46 | 54.49 | 11.46 |
| 4 | 32 | 276.35 | 54.13 | 32.67 |

25 GB/s と上表を組み合わせると、1行の2台構成で短縮できる局所時間の試算は 43.3 µs である。4台の1行は、3方向が同時に転送できる場合の 43.7 µs から直列の場合の 123.2 µs まで。いずれも転送と計算が重ならず、イベント・ホスト集合の追加時間を0と置いた条件付きの値である。

4入力 BF16 加算だけを R9700 1台に置いた場合の前後は、5,120要素で 4.508 → 3.628 µs、163,840要素で 4.847 → 4.393 µs、1,048,608要素で 8.941 → 9.251 µs だった。最後の形状では初版のスカラー実装が10.855 µs まで退行した。ベクトル化でその差を縮めたが、基準の動的ループに対して速度の優位はない。4台の各 rank が同じ順序で加算できる点も採否に含めた。

大きな語彙では両比較ともローカル処理は3起動である。候補では部分最大値、行内最大値、rank 間最大値の順に求める。

各リンクが独立して同時に帯域を使える4台構成では理想転送時間差は約39.73 µs/行まで縮む。追加の pack、イベント待機、ホスト経由の転送、既存カーネルとの重なりを含む端から端の効果は未確定である。特に2台の StreamSignal には CPU 集合を省ける利点があるため、送信量の比を tg の速度比に換算できない。

片方向フォールバックは全方向 `P(P−1)` 本のうち不通の方向だけで D2H と H2D を行う。1方向のみ不通なら、全方向をホスト経由にする場合に比べ、ホスト経由の方向数は2台で 2→1、4台で 12→1。従来のホスト上の加算と新経路の GPU 上の加算では処理も異なる。

### ローカル処理を複数 GPU に適用するときの見積もり

ここでいう局所時間は各 rank のカーネル時間である。新旧で同じ形状・同じ選択条件を満たし、その処理がボトルネックの時間に占める割合を `f`、局所時間の短縮率を `d` とすると、他の時間が一定の場合の速度比は `1 / (1 − f × d)` となる。

| 項目 | 2台・4台で期待できる範囲と条件 |
| --- | --- |
| EXL3 混在投影 | 対応する各 rank で2投影の起動が6→3。表の形状なら局所時間の目安は約51%減。語彙・出力列の分割で形状が変わる場合は再計測が必要 |
| WMMA 256行 | 同じタイル配置・十分な出力列がある場合、対象 GEMM の時間を約30%減として試算する |
| QSA | 同じブロック数と行数を処理する rank では top-k の局所時間が約60〜74%減。score 計算と sparse attention は個別に計上する |
| HyperApply・RoPE | hidden・整列条件がそろう小バッチで HyperApply は約62%減、RoPE は約22〜27%減。256行の HyperApply は実質同等 |
| PLE | 同一プロセスの共有ホストテーブルで1回の取得が約14〜17%減。rank 数を掛けた速度向上は見込まない。並列呼び出し時のキャッシュ競合は要実測 |

| EOS 無視・readiness・計測ツール | 動作や観測方法を追加する項目。カーネル速度の改善は計上しない |

### 高並列の回帰調査

32要求で整数を列挙するチャットを使い、要求ごとに48トークン、計1,536トークンを生成した。早期に EOS が出る短い入力だけでは検出できなかったが、移植当初はページ境界直前の位置47で、単独 decode がトークン ID −1 を返すことがあった。K=4 固定では完走した。prefix cache 無効時も2回の比較では通ったが、別の起動で再発した。逐次 GDN verify に切り替えた場合も再現した。

- 要求を投機に割り当てた後、残りが1トークンなら同じセッションでターゲットの1行を実行する。バッチ検証結果を全要求が消費する前にこの単独 forward を実行すると、ターゲットの中間結果を上書きできる。線形の適応型 verify では draft 数がゼロの要求も、アンカー1行として同じターゲットバッチに含めた。単独 forward が必要な経路は全要求の採否処理後に実行する。
- 検証幅を縮めたときは、drafter への提案数もその幅にそろえる。ページ境界をまたぐ保存に対応するセッションでは、境界の手前で投機を打ち切らない。初回の prefix 状態保存に実行ストリームを渡し、別ストリームでの重複保存を取り除いた。
- 検証の出力に無効なトークン ID が含まれていた場合は、要求の生成履歴に追加する前にエラーとする。
- 4要求で48トークンずつ生成する高受理率の入力では、初期 K=4 のままでは基準の161.22 tok/s に対して140.30 tok/s だった。設定上限が許す小バッチでは初回 K=5 とし、16要求を超える場合は最大4に抑える。

32要求を8件ずつのサブバッチに分割する案は、prefix cache 有効時に187.62 tok/s だった。16件ずつと最大64行ずつの案は反復でエラーを再現した。採用版は要求数による分割を追加せず、アンカー行をほかの検証行と一緒に処理する。

| 同時要求数 | prefix cache | 各回の出力 | 基準版（tok/s） | 採用版（tok/s） | 変化 |
| ---: | --- | ---: | ---: | ---: | ---: |
| 4 | 有効 | 192 | 160.19 | 173.12 | +8.1% |
| 32 | 有効 | 1,536 | 190.60 | 205.91 | +8.0% |
| 32 | 無効 | 1,536 | 215.07 | 235.98 | +9.7% |

Qwen3.8-27B EXL3 と BF16 drafter、設定上限 K=5、1要求48トークンを使用した。起動後1回を除いた中央値である。基準版は各条件6回、統合版の32要求は各8回測定した。32要求の全反復で生成 ID が基準版と一致した。初期 K の調整は4要求、アンカー行の採否は32要求で切り分けた。早期 EOS を含む別の入力では初期比較の合計出力が655個と701個に分かれた。同じ入力で固定 K の生成列は32要求すべて一致し、通常 decode でも起動・反復により生成数が変わった。この入力の速度比は採否に使っていない。

受理の統計は、検証した提案総数に対する受理総数を `DFLASH2_ACCEPTANCE_RATE`、提案を検証した要求・ラウンドのうち全提案を受理した割合を `DFLASH2_FULL_ACCEPT_RATE` とした。バッチ全体のラウンド数を後者の分母に使うと、同時要求時に1を超えていた。

### 機能検証

実サーバーで先頭に停止トークン ID 248046 を返す同一プロンプトを使った。通常は1トークンで `stop`、`ignore_eos=true` では同じ停止 ID を先頭に含む6トークンで `length` となった。別に起動した HTTP サーバーでは、`/readiness` が200を返し、同じサーバー配下の compute を終了すると503になった。

1本の48トークン生成の最初のトークンが届いた時点で、約540トークンの入力を4本追加して計測した。prefill chunk とステップ予算はともに64。prefix cache 無効、通常 decode の比較で、統合版の出力間隔 p95 は割り込み間隔0で約80 ms、間隔1でも約80 ms だった。元のスケジューラでもこの入力は decode を優先できるため、このケースで待ち時間短縮は観測していない。
