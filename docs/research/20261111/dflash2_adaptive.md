# DFlash2 の適応制御の調査

## 計測条件

R9700（gfx1201）、Qwen3.8-27B EXL3 4bpw mul24、KV cache FP8、短い benchmark prompt、
出力上限 160 token、greedy、prefix cache 無効。各実行で同時 request を投入し、
全 request が生成中の区間の合計 token/s を計測した。性能差は繰り返し測定して判定する。
各実行は `/tmp/r9700.lock` を取得する。上表の初回測定にはシステム Python の標準ライブラリで
作られた driver を使用し、再測定以降は `/tmp/venv-so` を使用する。

CPU の時刻から計測した通常 decode の中央値を以下に示す。`forward` は投入から戻るまでの
時間、`sync` は sample の host 転送待ち、`total` は scheduler を含む step 全体である。
同時 64 の値は 26 step、同時 32 は 27 step、同時 16 は 32 step、同時 8 は 84 step、同時 4 と 2 は各 112 step、
同時 1 は 166 step の中央値である。

## 選択ロジックの試作

位置 i の条件付き受理確率を EMA で保持し、そこに到達した位置のみ成功・失敗を更新する。
先に拒否された位置より後は観測されていないので更新しない。K 個の候補に対する期待受理数は、
各位置までの条件付き確率の積の和である。各 request の選択肢を 0 行（投機なし）、
または K+1 行で表し、同時に投機する request 数と合計検証行数ごとの最大期待受理数を動的計画法で求める。
測定した各形状の費用を与え、batch 全体の期待生成 token 数を費用で割った値を比較する。
直前の選択肢の予測値が最良値に近い場合には維持する。選択ロジックの CPU テストで小規模問題の
全組合せと照合した。

このロジックはまだ runtime に接続されていない。投機停止中は通常 decode の target tap を
各 request の drafter 履歴に追加し、再開時の位置と sampling 状態を維持する必要がある。
また、停止した request の定期的な試行と観測されない形状のコスト推定が必要である。

CPU 試作で候補数を 8 / 16 / 32 / 64 としたときの選択時間は、各 1 回の参考値で
0.026 / 0.200 / 1.375 / 9.663 ms だった（K 上限 7、最適化ビルド）。64 件の全探索は
通常 decode の時間に対して無視できず、費用の下限による枝刈りなどが必要である。
この値は GPU を用いた throughput の判定ではない。

同時に投機する request 数を 8 以下に制限した試作では、候補 8 / 16 / 32 / 64 件の
参考値は 0.032 / 0.065 / 0.150 / 0.378 ms だった。上限内で request の組合せと
行数を選べるが、8 を超える同時投機の最適値は対象外になる。
