# DFlash2 の適応制御の調査

## 計測条件

R9700（gfx1201）、Qwen3.8-27B EXL3 4bpw mul24、KV cache FP8、短い benchmark prompt、
出力上限 160 token、greedy、prefix cache 無効。各実行で同時 request を投入し、
全 request が生成中の区間の合計 token/s を計測した。性能差は繰り返し測定して判定する。
各実行は `/tmp/r9700.lock` を取得する。上表の初回測定にはシステム Python の標準ライブラリで
作られた driver を使用し、再測定以降は `/tmp/venv-so` を使用する。

CPU の時刻から計測した通常 decode の中央値を以下に示す。`forward` は投入から戻るまでの
時間、`sync` は sample の host 転送待ち、`total` は scheduler を含む step 全体である。
同時 64 の値は 26 step、同時 32 は 27 step、同時 16 は 32 step、同時 8 は 84 step、同時 4 と 2 は各 112 step、
同時 1 は 166 step の中央値である。

## 選択ロジックの試作

位置 i の条件付き受理確率を EMA で保持し、そこに到達した位置のみ成功・失敗を更新する。
先に拒否された位置より後は観測されていないので更新しない。K 個の候補に対する期待受理数は、
各位置までの条件付き確率の積の和である。各 request の選択肢を 0 行（投機なし）、
または K+1 行で表し、同時に投機する request 数と合計検証行数ごとの最大期待受理数を動的計画法で求める。
測定した各形状の費用を与え、batch 全体の期待生成 token 数を費用で割った値を比較する。
直前の選択肢の予測値が最良値に近い場合には維持する。選択ロジックの CPU テストで小規模問題の
全組合せと照合した。

このロジックはまだ runtime に接続されていない。投機停止中は通常 decode の target tap を
各 request の drafter 履歴に追加し、再開時の位置と sampling 状態を維持する必要がある。
また、停止した request の定期的な試行と観測されない形状のコスト推定が必要である。

CPU 試作で候補数を 8 / 16 / 32 / 64 としたときの選択時間は、各 1 回の参考値で
0.026 / 0.200 / 1.375 / 9.663 ms だった（K 上限 7、最適化ビルド）。64 件の全探索は
通常 decode の時間に対して無視できず、費用の下限による枝刈りなどが必要である。
この値は GPU を用いた throughput の判定ではない。

同時に投機する request 数を 8 以下に制限した試作では、候補 8 / 16 / 32 / 64 件の
参考値は 0.032 / 0.065 / 0.150 / 0.378 ms だった。上限内で request の組合せと
行数を選べるが、8 を超える同時投機の最適値は対象外になる。

## greedy 出力差の調査（途中）

同じ benchmark の先頭 request で、投機なしの同時 1 と同時 2 は 0 始まり 36 番目の
生成 token から異なった。同時 1 は token 1066、同時 2 は token 279 を選んだ。
各条件を再実行すると、それぞれ最初の実行と一致した。同時 2 の既存固定 K=1・2・7 と、
上限 K=7 の proposal を K=1 で切り詰めた場合は、いずれも同時 1 の投機なしと一致した。
したがって、この prompt では既存の固定 K と同時 2 の投機なしも一致せず、適応制御だけを
変更しても受け入れ条件を満たしたとは判断できない。logits の差の原因は調査中である。

不一致直前（同じ 36 token の生成後）の通常 decode logits を診断用ビルドで取得した。
同時 1 では token 1066 が 18.077957、token 279 が 18.022018、同時 2 では
それぞれ 18.014441、18.043940 で、両条件で実際に最大の token が異なった。
これは sampler の選択順だけではなく、target が出した logits に差があることを示す。
差が prefill、decode、量子化 kernel または蓄積状態のどこから始まるかはまだ未特定である。

同じ request の logits を各 step で比較したところ、prefill の最初の出力は bit 単位で一致した。
次の decode step では、同時 1 と 2 の logits の最大絶対差が 0.167146、RMS 差が 0.037770 だった。
この step の最大 token は両者とも同じで、36 番目に初めて最大 token が変わった。
前半層の中間出力による追加の切り分けは実行中である。

最初の decode step に 0〜7 層の hidden tap を付けて比較すると、層 0 の出力ですでに
5120 要素中 43 要素が異なり、最大絶対差は 0.000244140625 だった。層 1 では
3118 要素、層 7 では 4257 要素が異なった。prefill の出力 logits と入力 token は一致するが、通常 decode のバッチ数によって
最初の層から差が現れる。prefill で更新された内部状態そのものは未比較であり、層 0 内の処理は調査中。

層 0 の値を追跡すると、最初の decode step は同時 1 で 1 行、同時 2 ではもう一方の
request の prefill と混在して 88 行だった。両条件の `input_norm` と `gdn_qkv` は一致し、
同一入力の `gdn_z` 線形投影は 6144 要素中 1 要素が異なった。後段の `post_norm` は再び
一致したが、同一入力からの `mlp_gate` 投影でも 10 要素が異なった。少なくともこの条件では、
異なる行数で実行した線形投影の結果差が、後段の hidden 値と logits へ伝わっている。
「同時数だけ」の比較ではなく、prefill の混在を含む比較である点に注意する。

層 0 の最初の decode step で、`input_norm`、`gdn_qkv`、`gdn_b`、`gdn_a`、
`gdn_conv`、`gdn_recurrence` は一致した。`gdn_z` は 6144 要素中 1 要素が異なり、
その後 `post_norm` が一致する一方で `mlp_gate` は 17408 要素中 10 要素が異なった。
この測定では同じ入力から線形投影で差が出ている。1 行と 88 行では EXL3 の K 分割条件が
異なるため、分割数を 1 に固定した診断で関係を検証中である。

診断用ビルドで EXL3-INT8 の K 分割数を常に 1 に固定したところ、上記 prompt の
投機なし同時 1・同時 2、固定 K=7 同時 2、上限 K=7 を K=1 で切り詰めた同時 2 の token 列は一致した。ただし元の同時 1 の
出力とは 36 番目から異なり、元の同時 2 の出力とも 128 番目から異なった。
全員生成中の通常 decode は同時 1 で 27.75→22.98 tok/s（−17.2%）、同時 2 で
52.40→44.82 tok/s（−14.5%）になった。同時 2 の固定 K=7 は 105.06→98.01 tok/s
（−6.7%）、切り詰め K=1 は 61.50→56.52 tok/s（−8.1%）だった。各 1 回の参考値であり、
この分割固定を製品には
適用していない。今回の差には K 分割の違いが関与すると考えられるが、これだけで全条件の
数値差の原因を証明したわけではない。

切り詰め版と固定 K=7 の間にも差があった。例として S=3 では K=1〜4、S=4 では K=1〜3、
S=5 では K=1〜2 が、request 1 の 0 始まり 49 番目からそれぞれの固定 K=7 と異なった。
この例では前者の nominal verify 行数は 16 以下、固定 K=7 と一致した大きい K の nominal
行数は 17 以上であり、既存 EXL3 kernel の分割方針が変わる境界と重なる。ただし各 round の
実行状態も異なるため、境界との一致だけで原因を断定せず、分割固定で追加検証する。

分割数を 1 に固定した追加の同時 3 診断では、投機なしと固定 K=7 は request 1 では
一致したが、request 2 は 0 始まり 7 番目、request 3 は 8 番目から異なった。
したがって分割数の統一だけでは、この入力群の全 request の greedy 一致を保証できない。
分割 1 固定の同時 3 では、切り詰め K=1 は投機なしの全 3 request と一致したが、
固定 K=7 は request 2・3 でその両者と異なった。K 分割の固定後も検証行数や
複数 token の state 更新経路の違いが残るため、後続の診断が必要である。

別の診断では、17〜255 行でも低行数側と同じ K 分割方針を使った。今回の同時 2 では
投機なし・固定 K=7・切り詰め K=1 がすべて一致し、全員生成中速度は順に 52.90、107.68、
61.19 tok/s だった。ただし同時 1 の元の token 列とは 36 番目から異なり、速度も
27.75→26.69 tok/s（−3.8%）だった。各 1 回の参考値であり、この変更も製品には適用していない。

低行数側の K 分割方針を 17〜255 行にも使った同時 3 診断では、投機なしと固定 K=7 は
3 request とも一致せず、最初の差はそれぞれ 0 始まり 128・19・0 番目だった。投機なしの
request 3 は元の通常設定とも先頭 token から異なった。同時 2 の一致は一般化できない。
同じ分割方針で切り詰め K=1 も加えた同時 3 比較では、固定 K=7 と全 3 件で一致せず、
投機なしとは request 2 のみ一致した。単純に分割数を統一する 2 案のどちらも、現在の
出力を維持しつつ必要な greedy 一致を満たす解決にはなっていない。
