# Hy4 状態退避の調査

この文書は fork 専用の実装と検証の記録である。

## 既存状態

Hy4 は汎用 prefix cache を無効にし、各生成要求で `Target` を新規作成する。`Target::history` は処理済み token ID を保持し、Engram の `prior` と次の位置の両方に使われる。生成後の最後の出力 token は通常、その直前の forward の結果であり、まだ KV に格納されていない。DFly では一度に 6 token を検証し、受理数で history を縮めるが、生成上限や EOS により実際に出力した個数と履歴の長さが一致しない場合もある。したがって出力文字列や要求 token 数から KV の位置を推定してはならない。

rank 0 の `Residency` は 42 層の KV を所有する。各 slot は 294 byte の独自圧縮レコードである。層 0 と 1, 5, …, 41 の計 12 層は全位置の KV と indexer を持つ。残り 30 層は最大 518 slot の循環 KV を持ち、位置 modulo slot 数で参照される。indexer は 4 token ごとの BF16 128 要素の pooled key と、BF16 128 要素の pending key 12 slot を持つ。pending の配置は予約長に依存するため、保存時と復元時の予約長が異なる場合は移動先を計算し直す必要がある。

DFly の attention は対象層の KV を読み、draft 自身の KV は保存しない。継続生成には直近の hidden state と 5 層の選択結果も使う。新たな入力 token を forward してこれらを作り直す設計なら、その境界条件の正しさを検証する必要がある。iHC の中間値は forward 内の作業域に存在する。sampling は要求ごとの seed と位置から乱数を作る。ここでは進行中の生成を再開せず、新しい要求の sampling 設定を使用し、処理済み token 数を位置として復元する。

## サイズの計算

処理済み長を N、予約長を C とし、N が 12 以上で、未使用部分を除き pending 12 slot をすべて保存すると仮定した計算値は以下である。メタデータ、token ID、転送バッファ、アラインメントは含まない。sliding は未使用 slot を含め、予約された `min(C, 518)` slot をすべて保存する。

`12 × (294 × N + 256 × floor(N / 4) + 3072) + 30 × 294 × min(C, 518)` byte。

| N | C ≥ N の場合の計算値 |
|---:|---:|
| 2,048 | 13,403,832 byte |
| 8,192 | 39,798,456 byte |
| 32,768 | 145,376,952 byte |
| 100,000 | 434,205,624 byte |

長い履歴では sparse KV と pooled key の増分は 12 × (294 + 64) = 4,296 byte/token である。これは実測転送量ではない。

## RDMA の現状と設計上の課題

既存プロトコルは 4 表のアドレスと rkey を交換し、Engram 表を remote read のみで公開する。サーバーは 1 接続を処理し、制御接続では切断まで byte を読み捨てる。保存領域を公開するには QP と MR の書き込み権限、制御メッセージの枠組み、接続障害後の世代管理が必要になる。既存表の登録領域とは別に保存領域を割り当てる必要がある。

候補は二重領域への書き込みと、全データの完了・チェックサム検証後に制御経路で世代を切り替える方式である。接続断や容量不足時には旧世代を維持する。復元側はモデルと実際の重み、配置、KV 形式、予約長などの同一性と token ID の完全な prefix 一致を検証し、転送と検証がすべて成功するまで状態を使用可能にしてはならない。途中まで GPU に書き込んだ場合も、通常 prefill が全必要領域を再構築することを確認する必要がある。実装後の状態と検証結果は後述する。

## 状態転送の試作

既存の Engram サーバーと別のプロセスが `10.255.254.1:19391` を使用する。容量を指定した二つの独立した RDMA 登録領域を確保し、未使用側に WRITE して SHA-256 をサーバーで照合した後、世代を切り替える。READ 後もクライアント側で SHA-256 を照合する。接続は逐次処理する。対象は RAM のみで、サーバーを終了すると保存内容は失われる。Engram 表の MR や既存サーバーのプロセスは変更しない。

2026-11-19、1 世代 33,554,432 byte のサーバーに対し、17,825,803 byte の合成データを保存・復元した。CMake で構築したテストの 1 回の実行では、接続・SHA-256・コピーを含む保存が 0.106836 秒（0.167 GB/s）、復元が 0.064890 秒（0.275 GB/s）だった。GPU コピーを含まず、モデル状態や再起動時間の測定ではない。容量超過の保存が拒否され、旧世代が保持されること、次世代へ切り替わることも確認した。

`test_hy4_snapshot_rdma` はこのサイズの試験用サーバーを別途起動して実行する必要がある。当該試験用サーバーは試験終了後に停止した。


## エンジンへの接続と prefill 境界

GPU の rank 0 から、sparse 12 層の処理済み KV、完成済み indexer group、pending 12 slot と、sliding 30 層の全循環領域を取得する。予約長と処理済み ID 列をヘッダーに持たせ、同じ予約長に限り復元する。DFly の hidden と選択結果は保存せず、復元後に少なくとも 1 token の forward を行って作り直す。入力が保存済み token 列と完全一致するだけで後続 token がない場合は、通常 prefill に戻る。

生成中の KV をそのまま保存した初期案では、2,303 token を復元した後の 256 token が同じ 2,305 token を通常 prefill した場合と一致しなかった。生成中と prefill 中では chunk の形状や計算経路が異なるが、不一致の原因は特定していない。現在は prefill の最後の完全な chunk の直後を保存し、以降の未保存部分を通常 prefill する。chunk サイズも照合する。同一プロセス内で 1,024 token の時点の状態を退避し、全 KV と indexer をゼロにした後に復元した試験では、復元前後の保存バッファが一致し、2,048 token 入力に対する通常生成の 256 token が対照と一致した。別プロセス間でも、2,048 token を保存し 2,305 token の入力を再開した場合、通常生成の 256 token が通常 prefill と一致した。

`SHELF_HY4_SNAPSHOT=1` を compute の環境に設定すると、生成要求が正常終了した際に上記境界を保存し、次の要求で最新世代の prefix 一致を試みる。Python の `shelf-server` から起動する場合も同じ環境変数を継承させる。停止前の最後の成功要求が保存単位で、生成済み token および未完成の chunk は次の入力で再 prefill する。完全 chunk の境界が少なくとも 12 token かつ sliding の予約 slot 数以上にならなければ保存せず、以前の世代を維持する。対象は単一要求の Hy4 エンジンであり、他モデルや複数セッションには対応しない。

ID 列の SHA-256 に加え、実行ファイル、GPU の ISA・PCI 配置と runtime、予約長、expert 配置、量子化 tensor の metadata と GPU への重み転送時の実データ、履歴で参照する Engram 行を fingerprint に含める。重みの SHA-256 はモデルを GPU に転送する際に算出するため、起動時間が増える。既存 Engram サーバーに表の digest はないので、履歴で実際に参照した行を照合する。モデルの mmap 元ファイルと Engram 表は、要求の処理中に変更しない運用を前提とする。snapshot 専用サーバーの接続・形式・checksum・fingerprint・prefix 照合が失敗した場合は、GPU への復元を使わず通常 prefill に戻る。Engram 表自体を配信する既存サーバーが停止した場合は、その表を取得できないため従来どおり推論を続行できない。

独立した転送試験では 145,376,952 byte の合成データがバイト一致し、接続後の RDMA 発行から完了までの合計は WRITE 0.081329 秒（1.788 GB/s）、READ 0.073274 秒（1.984 GB/s）だった。コピー、接続、checksum を除いた区間で、GPU 往復の値ではない。状態サーバーに故障注入してデータを変更した場合、READ 後の checksum が不一致となり拒否された。

### 起動例

別ポート用バイナリをこの worktree で構築し、リモートに配置する。`536870912` は 1 世代あたり 512 MiB で、実際には 2 世代分が RDMA 登録される。Engram サーバーとは別の memlock 上限が必要であり、空きメモリとユーザーの上限を確認する。

```sh
c++ -std=c++20 -O2 -Iinclude tools/hy4_flash/snapshot/server.cpp -libverbs -lcrypto -o /tmp/shelf-hy4-snapshot-server
scp /tmp/shelf-hy4-snapshot-server user@192.168.0.148:/tmp/shelf-hy4-snapshot-server
ssh user@192.168.0.148 '/tmp/shelf-hy4-snapshot-server 536870912'
```

このサーバーを稼働させたまま、RDMA 対応ビルドの `shelf-server` を `SHELF_HY4_SNAPSHOT=1` で起動する。`hy4-llm` の管理プロセスから起動する場合は、管理プロセスにこの環境変数を継承させ、実行する compute を本ブランチの RDMA 対応ビルドに切り替える必要がある。統合は別途必要であり、管理プロセスが既に起動中の場合はその環境も確認する。成功した要求の後、`snapshot_saved_tokens` のログを確認し、必要に応じて `curl -X POST http://127.0.0.1:8123/admin/snapshot` を実行して最後の状態を再送してから停止する。管理 endpoint は要求中なら完了を待ち、退避できない場合は HTTP 503 を返す。自動保存に失敗した場合も、プロセス内に保持した直近の候補があれば、この endpoint で再送を試みる。再起動後に同じ ID 列を先頭に含む次の要求を送ると `snapshot_restored_tokens` が記録される。退避先のサーバーを終了すると保存内容も消える。

## 実機検証と時間

2026-11-19、R9700 と V620 2 台、4 bpw、Engram RDMA、chunk 1,024、greedy、各条件 1 回。2,048 token の既存入力 ID 列を反復して各長さを作った。保存側は指定長を prefill し 1 token 生成、停止後の入力はその ID と追加 1 token を続けた。再起動した compute サーバーの復元後、独立した通常 prefill、および fingerprint を変更した際のフォールバックの 256 token は全条件で一致した。保存側では compute の `snapshot` 管理操作による再送も成功した。

GPU 取り出しと保存処理は別区間。保存処理には必要な Engram 行の再照合、checksum、接続、ホスト側コピー、RDMA を含む。復元処理には checksum、fingerprint 照合、通信、GPU コピーを含む。READ / WRITE は接続確立・コピー・checksum を除き、RDMA の発行から完了までの区間だけを合計した GB/s。総時間は compute プロセスの起動から最初の出力 token までで、HTTP サーバーやクライアントの起動は含まない。

| 保存 token / 生成 | 保存 byte | GPU 取出 + 保存 秒 | 復元処理 秒 | WRITE / READ GB/s | 復元の総秒 | 通常 prefill の総秒 |
|---|---:|---:|---:|---:|---:|---:|
| 2,048 / 通常 | 13,412,128 | 0.0043 + 0.3335 | 0.2782 | 1.694 / 1.831 | 62.55 | 25.95 |
| 2,048 / DFly | 13,412,128 | 0.0044 + 0.3346 | 0.2764 | 1.659 / 1.858 | 64.23 | 25.99 |
| 8,192 / 通常 | 39,831,328 | 0.0095 + 1.0175 | 0.8755 | 1.761 / 1.929 | 64.36 | 37.90 |
| 8,192 / DFly | 39,831,328 | 0.0095 + 1.0115 | 0.8523 | 1.793 / 1.960 | 64.77 | 38.31 |
| 32,768 / 通常 | 145,508,128 | 0.0296 + 3.6566 | 3.1515 | 1.841 / 1.949 | 66.65 | 95.19 |
| 32,768 / DFly | 145,508,128 | 0.0292 + 3.6517 | 3.3867 | 1.832 / 1.951 | 65.82 | 95.62 |

重み転送時の SHA-256 計算により、復元側の起動完了は約 62〜64 秒、照合を無効にした通常側は約 22〜23 秒だった。この条件では 2k / 8k の総時間は復元の方が長く、32k は約 28〜30 秒短かった。100k は未測定である。生ログは測定ホストの `/tmp/hy4-state-serve-matrix/` と `/tmp/hy4-state-serve-matrix-final.out` にある。

## 故障注入と管理操作

同じ 2k 入力で、容量を 1 MiB に制限した状態サーバーへの保存失敗、状態サーバー停止後の接続失敗、保存済みバッファの 1 byte 変更による checksum 不一致、RDMA READ 用 QP を error にした接続障害をそれぞれ注入した。いずれも通常 prefill に戻り、greedy 256 token が対照と一致した。6 条件すべてで保存 payload の fingerprint を変更し、checksum 自体は再計算した場合も、照合で拒否して 256 token が一致した。

GPU への復元では、最初の sparse KV をコピーした後の次の sparse KV コピーに HIP エラーを注入した。復元失敗後に通常 prefill を行い、256 token が対照と一致した。これは API 呼び出しに対する一度だけの故障注入であり、GPU の物理故障を再現した試験ではない。

実際の HTTP サーバーでは、候補がない場合の `POST /admin/snapshot` が 503 を返し、2,225 入力 token の要求後には 13,412,128 byte の再送が成功した。HTTP の応答と生成要求との排他は、別途単体テストでも確認した。既存 Engram サーバー自体の停止は通常 prefill を可能にする試験には含めていない。Engram の RDMA ソースが停止すれば、前述のとおり推論自体が継続できない。

上書き中の原子性は、旧世代を保存した後、次の WRITE の 4,194,304 byte 完了後に QP を error にする故障注入で確認した。新しい保存は失敗し、旧世代はバイト一致で読み出せた。既存 Engram RDMA の 4 表合計 100 万行と端の行の照合、および時計注入による READ timeout 後の接続破棄テストも通過した。

通常生成と DFly の既存 2,048 token 入力でも、DFly 側で 1,024 token 時点の GPU 状態を全消去して復元した後の 256 token は、既存コミットの通常生成および最終バイナリの通常生成と一致した。最終バイナリの通常生成を別プロセスで 3 回再起動した結果も、既存コミットと 256 token 一致した。既存コミットのソースから別ディレクトリへ再ビルドした対照、および新旧の shared library を入れ替えた対照も一致した。

一方、これらの確認前に snapshot を無効にした通常生成が 1 回 SIGSEGV で終了した。システムログには `ld-linux-x86-64.so.2` 内、アドレス `0x404` へのアクセスとして記録された。core dump は得られず、デバッガー下の再実行、上記 3 回の再起動、さらにデバッガー下での 5 回の再起動では再現しなかった。原因と本変更との関係は未特定であり、再発しないとは確認できていない。
